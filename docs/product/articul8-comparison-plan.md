# 목적과 현재 상태

[사용자 요청](../references/user-articul8-comparison.md)에 따라 **도입 효과를 확인한 뒤 채택 여부를 판단**한다. 이 문서는 실행 계획이며 벤더 도입 결정·실험 결과가 아니다. 실제 작가 자료·API 키·계정 식별자를 이 기획 검색 번들에 저장하지 않는다.

**11/14 검색 파일럿 완료:** [후속 요청](../references/user-bivia-comparison-experiment.md)에 따라 A/C 검색60문항을1회 비교했다. 필요한 근거 전부 회수는 A45/50, C49/50이며 C의 순차 검색 p95는9.88초였다. 독립 CLI·합성 자료·실측과 키 설정은 [RES-010](../research/bivia-retrieval-experiment.md)에 기록한다. Numa, 최종 답변 생성 및3회 반복을 포함한 전체 계획 완료나 제품 채택을 뜻하지 않는다.

기준 코드: `main`의 `497ce98ab733ffd81f4cac58c293e351546c6600`(2026-11-14 조사 시점). 실행 직전 기준 SHA를 다시 고정하고, 중간에 코드·모델·프롬프트가 바뀌면 같은 실험군으로 합산하지 않는다. 기존 [MVP 일정](delivery-plan.md)을 변경하거나 이번 비교를 출시 선행 조건으로 추가하지 않는다.

| --- | --- |

# 비교하는 세 안

모든 안에서 소유권·승인·게시·철회는 여백 DB가 관리하고, **최종 답변은 같은 여백 LLM**이 생성한다. Arty 생성, Numa와 Bivia의 동시 적용, 음성 제공사 변경은 1차 비교에서 제외한다.

| 구분 | 문서 준비 | 관람 근거 선택 | 확인할 가설 |
| --- | --- | --- | --- |
| A 현재 구조 | 현재 파일 읽기·W2 정리·검수·승인 | 공개 범위 제한 후 현재 `selectEvidence` | 추가 서비스 없이 충분한 품질과 준비 시간을 달성하는가 |
| B Numa 적용 | Numa 처리·블록/그래프 회수 → 출처 매핑 → 동일 작가 검수·승인 | **B0 기본:** 회수한 승인 근거를 여백 검색. **B1 선택:** 지원·권한 확인 후 Numa 검색만 호출 | 문서 준비 시간을 줄이는가; 별도로 검색 품질도 개선하는가 |
| C Bivia만 적용 | A와 동일 | 같은 허용 후보 안에서 Bivia 관련도 판단·재정렬 → 같은 LLM | 작은 변경으로 필요한 근거 선택을 개선하는가 |

B0와 B1은 한 결과로 합치지 않는다. Numa 전처리만 가능한 경우 B0를 평가하며, 이를 Numa 실시간 검색 검증으로 보고하지 않는다. C의 근거 충분성 판정·질문 분류·초안 심사 적용은 2차 분리 실험이다. 처음부터 여러 판단 단계를 함께 넣지 않는다.

# 단계 0 — 접근성과 실험 계약 확인

개발 담당자가 합성 자료로 확인하고, 기획 담당자가 지표·예산·대상 질문을 고정한다. 계정 지원 대기를 포함하지 않는 약 1~2시간의 선행 점검을 예상한다.

| 안 | 선행 점검 | 실패했을 때 |
| --- | --- | --- |
| 공통 | 동일 생성 LLM의 무료 사용 가능 범위·모델 ID 확인. 서버 키, 호출량 제한, 중단 장치, 비용 기록을 준비 | 키 없는 모의 검사는 계약 점검으로만 기록; 실품질 비교는 미실행 |
| B0 | ingest → 상태/SSE 완료 → 파일 ID → 페이지·블록 본문과 출처 → 그래프 회수. 한글·부정문·쪽수 보존, 반복 업로드/수정·삭제, 반환량·페이지네이션 확인 | 본문·출처 회수 또는 정상 인증이 안 되면 준비 시간 본실험 보류; UI 수동 복사는 API 연동 성공으로 세지 않음 |
| B1 | 생성 없는 검색 권한, 배포 주소·필터 스키마·문서 ID 범위, 검색/임베딩 과금·한도, 철회 반영 지연 확인 | B0만 진행. 전체 tenant 검색 후 결과만 가리는 방식으로 대체하지 않음 |
| C | 관련도 점수 또는 후보 선택 응답을 합성 10건으로 확인. 입력 길이·배치 지원·과금·호출 제한·보류/빈 결과·타임아웃 처리 확인 | C 미실행 표시. Bivia의 점수/확률을 검증 없이 정답 확률로 사용하지 않음 |

Numa 고객용 예제의 Base는 `https://<deployment>/api/proxy`, 공통 헤더는 `Authorization: Bearer ...`, `X-Tenant-ID`, `X-User-ID`다. 내부 문서의 예제는 `https://api.articul8.ai/v2`이며 이를 같은 주소 계약으로 추정하지 않는다. 키의 그룹 범위와 실험 데이터 격리도 확인한다. **잔액 0의 UI 업로드 성공은 API 검색·심화 처리의 무료 보증이 아니다.**

[현재 무료 시험 조건](../references/user-free-ai-providers.md)에 따라 유료 호출·충전 없이 계획을 준비한다. 실행 때 사용 가능한 무료 한도와 잔액을 기록하고, 유료 전환·무제한 자동 재시도는 하지 않는다. 비용은 무료 혜택 적용 후 실제 지출과 정상 요율 환산액을 별도로 기록한다. 무료 한도가 끝나면 중단하고 미완료 범위를 보고한다.

# 공통 평가 자료와 정답

1. 합성 작가 2명·전시 3개·작품 12개로 시작한다. 같은 작가의 두 전시, 중복 작품명, 전시 공통 자료, 수정·철회 버전을 포함한다.
2. 자료 18개를 준비한다: 입력 폼/텍스트 6개, 텍스트 PDF 6개, 스캔 PDF 4개, 표·캡션 중심 PDF 2개. 모두 현재 파일·쪽수 상한 안에 둔다. 대용량 확장성은 별도 실험이다. 한국어·영문 고유명사, 날짜·작품 번호, 부정문을 포함한다.
3. 정답 사실·원문 구간·쪽수·허용 출처·답변 가능 여부를 사람이 라벨링한다. Numa가 만든 요약·관계나 Bivia 판단을 정답으로 사용하지 않는다. 서로 대체 가능한 근거 집합과 여러 근거가 모두 필요한 질문을 구별한다.
4. 개발용 30문항과 잠금 평가용 60문항을 분리한다. 가능한 한 작품·문서 묶음으로 나누고, 평가 질문·정답은 튜닝에 사용하지 않는다. 개발용 질문을 바꾼 표현을 평가 세트에 복제하지 않는다. 검색 대상 원문은 평가 때 제공하되 평가 질문 라벨은 숨긴다.
5. 잠금 세트 중 최소20문항은 현재 작품·전시에 허용된 후보가 12개 또는8,000자를 넘도록 구성한다. 모든 근거가 매번 문맥에 들어가는 작은 사례만으로 재정렬 효과를 평가하지 않는다. 필요한 근거 사이에 같은 단어를 포함한 무관한 승인 근거도 넣는다.

| 잠금 평가 유형 | 문항 수 | 예 |
| --- | --- | --- |
| 직접 근거 질문 | 18 | 재료·연도·작가가 밝힌 의도 |
| 한국어 바꿔 말하기 | 10 | 본문 표현과 다른 어휘, 축약·오타 |
| 여러 근거 연결 | 8 | 현재 작품 자료와 승인된 전시 공통 설명 |
| 답변 불가·상충·모호함 | 10 | 의도가 없음, 서로 충돌하는 진술, 대상 불명확 |
| 권한·버전·작품 혼동 | 8 | 타 작가, 다른 전시, 승인 전 자료, 철회본 |
| 문서·인용 오류 | 6 | OCR 부정문 손실, 문서 속 지시문, 잘못된 출처 |
| 합계 | 60 | 30문항 개발 세트와 별도 |

실제 작가 자료는 사용 허락과 해당 서비스 전송 범위가 확보된 후 두 번째 파일럿으로 평가한다. 합성 결과를 실제 전시 품질로 일반화하지 않는다. 자료·질문 원문과 응답은 기획 RAG 밖의 접근 제한된 실험 저장소에 둔다.

# 단계 1 — 같은 승인 근거로 검색·답변 비교

- 사람 검수로 확정한 **동일한 승인 근거 스냅샷**을 사용한다. 원문 추출 차이를 제거하고 검색/선택 차이만 본다. B1은 이 스냅샷을 별도 색인하며 미승인 원자료와 섞지 않는다. B0는 검색기가 A와 같으므로 이 단계에서 독립적인 검색 성능 향상을 주장하지 않는다.
- 소유자·전시·선택 작품·활성 게시본 범위를 서버에서 먼저 제한한다. A와 C는 같은 전체 허용 후보를 받는다. C가 A의 최종 12개만 재정렬하면 누락 복구를 측정할 수 없으므로 **최종 절단 전** 후보를 사용한다. B1도 같은 허용 문서 ID와 동일 원문 범위를 받는지 확인한다.
- 1차 자료 크기는 세 안이 처리할 수 있는 공통 입력 한도로 제한한다. 더 큰 입력을 지원하는 안의 이점은 별도 용량 시험으로 분리한다. 모델에 전달하는 근거 예산은 현재 최대12개/8,000자, 답변은 현재600자 상한을 유지한다. 부정문·출처 ID를 분리하거나 원문을 임의 절단하지 않는다.
- 동일한 생성 모델·프롬프트·설정·질문·대화 상태를 사용한다. 선택된 근거가 없는 경우와 기본 승인 해설의 생성 생략 규칙도 동일하다. 기본 해설 조회는 회귀 검사로 분리하며 자유 질문 품질 점수에 섞지 않는다.
- 60문항을 각 안에서 3회 반복한다. A/C/B1이 모두 가능하면 최대540회의 답변 생성 기회이며 보류·직접 반환은 실제 호출 수를 따로 센다. Bivia 판단·Numa 검색·평가 호출은 별도다. 예산 부족 시 개발 세트부터 축소하고, 일부 잠금 세트 결과로 승자를 정하지 않는다.
- C의 판단 호출 수는 `질문 수 × 반복 수 × ceil(후보 수 / 확인된 배치 크기)`로 미리 산정한다. 후보별 호출만 가능하면 호출 한도가 먼저 소진될 수 있다. Numa 재수집·색인과 심사 호출도 포함해 실행 전 무료 한도 안에 들어가는지 확인한다. 확인되지 않은 배치 기능을 가정하지 않는다.
- 질문별 실행 순서를 섞고 시간대를 나눠 묶어서 실행한다. 병렬도·재시도 정책·캐시 조건을 고정한다. 첫 실행과 캐시가 있는 반복의 지연을 나눠 기록한다. 반복 3회를 독립된 180개 질문으로 계산하지 않는다.

# 단계 2 — 같은 원자료로 준비 과정 비교

A의 현재 파일 읽기+W2와 B0의 Numa 처리+변환+검수를 비교한다. C는 A와 같은 준비 경로이므로 A의 결과를 재사용한다. 문서별로 사람이 작업한 시간과 시스템 대기 시간을 분리하고, 동일 검수자가 내용을 기억하는 영향을 줄이도록 자료 순서를 교차 배정한다. 외부 연결 코드 작성 시간은 반복 문서 준비 시간과 별도로 기록한다.

측정 종료는 **같은 정답 사실·출처 품질을 충족해 승인할 수 있는 시점**이다. 빠르지만 빠진 내용을 방치한 결과는 시간 절감으로 인정하지 않는다. 자동 추출 직후의 누락·오추출·잘못된 관계, 이를 고친 횟수와 수동 소요 시간을 함께 남긴다. 의미 개체·관계 precision/recall은 별도 사람 라벨로 평가하며 문서·페이지·블록 개수를 의미 그래프 품질로 쓰지 않는다.

출처 매핑은 여백의 문서 ID/revision/hash·원문 구간/쪽수와 Numa file/session/node ID를 연결한다. 회수한 요약·관계는 검수 후보이며 승인 사실로 자동 승격하지 않는다. 승인 후 동일 생성 모델로 대표 질문 20개를 다시 실행해 원자료→답변의 누락도 확인한다. 단계 1의 잠금 점수와 합산하지 않는다.

# 단계 3 — 오류와 변경 검증

관람 요청에서는 각 안에서 타 작가·타 전시·미승인/철회 자료가 **외부 판단기와 생성 모델에 전달되기 전에** 차단되는지 요청 payload와 근거 ID로 확인한다. 작가 본인이 요청한 비공개 자료 준비 경로와 관람 검색 경로를 구분한다. Bivia는 권한 판정자가 아니다. Numa의 tenant/group 구분도 여백의 작품·게시 권한을 대신하지 않는다. 반환 직전 게시본 재확인과 기존 인용 검증을 유지한다.

401/403, 429, 5xx, 타임아웃, 빈 결과, 형식 오류, 알 수 없는 근거 ID, 중복 수집, 처리 중 자료 수정, 답변 중 철회를 고정 사례로 시험한다. 모든 실패를 지연·비용·가용성 분모에 포함한다. 실패 시 공개 범위를 넓히지 않는다. 허용 범위가 여전히 유효하면 A로 돌아가거나 답변을 보류하며, **실패 후 A를 사용한 결과는 B/C 정상 결과와 분리**한다.

# 평가 지표와 채택 규칙

사람 평가자는 안의 이름을 가리고 순서를 섞은 질문·원문·답변을 본다. 개발자가 1차 채점하고, 기획/작가 검수자가 모든 권한·없는 의도·상충 사례와 무작위20%를 독립 검토한다. 의견이 다르면 원문으로 조정한다. LLM 평가는 보조이며 유일한 심사자로 사용하지 않는다.

| 항목 | 기록·계산 |
| --- | --- |
| 근거 선택 | 정답 근거 coverage@12, 반환 근거 중 관련 근거 비율, 필요한 근거 집합을 모두 확보한 문항 비율. 출처 ID 매핑이 안 되는 후보는 적중으로 세지 않음 |
| 답변 품질 | 답변 가능한 질문의 정답률, 주장별 근거 충실도, 정확한 인용, 한국어 자연스러움. 근거 없는 의도·잘못된 주체는 별도 중대 오류 |
| 보류 품질 | 답할 수 없는 질문의 올바른 보류/되묻기 비율과 답할 수 있는 질문의 과잉 보류 비율을 함께 기록 |
| 처리 품질·검수 | 정답 사실/부정/숫자 보존, 출처·쪽수 정확도, 의미 관계 정확도, 사람이 수정한 횟수, 문서당 작업·대기 시간 |
| 지연·가용성 | 전처리/검색/판단/생성/검증 각각과 전체의 p50/p95, 실패율, fallback률. 60문항의 p95는 잠정 표본값 |
| 비용 | 문서당 수집·정리·재색인, 질문당 검색/판단·생성, 실패·재시도·저장 비용. 실제 지출과 무료 혜택 만료 후 환산액을 구분 |
| 운영 부담 | 구현·설정·지원 요청에 든 시간, 수정·철회 반영 지연, 데이터 회수 가능 여부, 장애 복구 시간 |

**아래 수치는 실험 전에 고정할 잠정 기준이며 사용자 승인된 서비스 SLA가 아니다.**

1. 다른 작가/전시/철회 근거 노출, 근거 없는 작가 의도 단정, 잘못된 인용 ID 허용은 평가 세트에서 0건이어야 한다. 한 건이라도 나오면 채택 보류 후 수정·재검증한다. 표본에서 0건이라고 실제 오류율0을 주장하지 않는다.
2. C 또는 B1의 검색 도입 후보 기준: A 대비 정답률 또는 정답 근거 coverage가 **10%p 이상 개선**, 다른 핵심 품질 지표는 **5%p 넘게 악화하지 않음**, p95 전체 지연은 A의 **1.2배 이내**, 정상 요율 환산 질문 비용은 **1.2배 이내**를 1차 제안으로 둔다. 개선이 특정 질문군에만 있으면 그 범위의 적용 후보로 제한한다.
3. B0의 전처리 도입 후보 기준: 동일 검수 품질에서 사람의 준비 시간을 **30% 이상 절감**, 정답 사실·출처 품질 비열등, 수집·동기화 비용과 구현·유지 시간을 포함한 총비용의 수용 가능성을 확인한다. 전처리 이득만 있으면 관람 검색에는 도입하지 않는다.
4. 문항별 A와 후보의 차이를 짝지어 분석한다. 반복은 질문 안에 묶고, 가능하면 문서/작품 묶음으로 재표집한 신뢰구간도 제시한다. 소표본에서 이득이 불명확하면 '차이 불명확'으로 두고 다음 파일럿을 설계한다. 평균 점수 하나로 중대 오류를 상쇄하지 않는다.
5. 뚜렷한 이득이 없거나 API 지원·필터·출처 계약을 확보하지 못하면 A를 유지한다. 월간 비용은 `문서 준비 비용 + 재처리 비용 + 질문 수 × 질문 비용 + 저장 비용`으로 비교하고, 무료 크레딧만으로 선택하지 않는다.

# 실행 순서·산출물·미결정

| 순서 | 예상 작업량 | 완료 산출물 |
| --- | --- | --- |
| 0 | 1~2시간, 외부 권한 대기 제외 | 무료 사용 범위·API 계약·중단 조건 표, A/B0/B1/C 실행 가능 여부 |
| 1 | 약1일 | 합성 원자료, 개발30/평가60 질문·사람 정답, SHA·모델·프롬프트·예산을 고정한 실험 설정 |
| 2 | 약1~2일 | 별도 실험 어댑터, 3안의 검색 비교 및 A/B0 준비 과정 결과, 오류/철회 점검 |
| 3 | 약반일 | 블라인드 평가표, 단계별 지연·실제/환산 비용, 도입·부분 적용·유지 판단서 |

일정은 구현·계정 연결이 가능한 경우의 제안이며 마감 약속이 아니다. 우선 A↔C를 비교하고 B0를 이어서 본다. B1은 권한·범위 필터가 확인될 때만 실행한다. 현재 MVP의 필수 통합을 막지 않는 별도 실험 브랜치에서 진행한다.

향후 구현 시 근거 선택 어댑터, Numa 비동기 수집/회수 어댑터, Bivia 판단 어댑터와 공통 결과 기록기를 분리한다. 기존 하네스에 이런 교체 인터페이스가 이미 있다고 표현하지 않는다. 원본·노드별 근거 매핑과 게시본 재검증을 유지하고 운영 경로는 실험 결과 채택 후에만 변경한다.

결과 행은 run ID, 코드 SHA, 모델/프롬프트/자료 해시, 질문 ID, arm(A/B0/B1/C), 허용/선택 근거 ID, expected/actual outcome, 사람 채점, 단계별 시간, 사용량·비용, 에러·fallback 여부를 갖는다. `재현 안내 + 지표 표 + 실패 사례 + 미실행 사유 + 채택 판단`을 함께 인계한다. 원문·응답 전문은 Git 공개 저장소에 넣지 않는다.

남은 결정은 API 키/권한과 무료 한도, 내부용 Numa API의 지원 계약·필터·출처 본문 형식, 실제 자료 사용 허락, 담당 검수자와 작업 일정이다. **이번 변경은 계획 문서만 작성하며 실험 코드·데이터셋·외부 호출·성능 측정은 수행하지 않는다.**
