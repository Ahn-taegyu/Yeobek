# 위키의 목적과 원본

**위키는 AI의 정보 검색·참조를 위한 내부 지식 구조다.** 작가는 일반 정보 입력·수정·검수 화면을 사용한다. 관람객은 공개 전시·작품 정보와 채팅을 이용한다. 두 사용자에게 내부 문서 ID·YAML·연결 그래프·RAG 설정을 보여줄 필요는 없다.

사용자는 **DB 원본 저장**을 선택했다. docs에서 참고할 것은 개념별 분리, 안정 ID, 속성·본문·출처, 관계와 상태다. 작가 원자료를 기획 docs나 기획 RAG에 저장하지 않는다. `.md` 파일, Obsidian Bases, 파일↔DB 동기화, 내보내기를 제품 MVP에 추가한다는 뜻이 아니다. 제품이 공식 OKF 전체 규격을 구현했다고도 주장하지 않는다.

# 개념과 관계

| 내부 문서 | 입력하는 화면 | 보존할 내용 | 연결 |
| --- | --- | --- | --- |
| 작가 | SC-A02 작가 홈 | 표시 이름, 소개, 작품 세계·작업 배경, 작가 공통 자료 | 소유자 계정과 구분한 artist ID; 여러 전시가 같은 작가 참조 |
| 전시 | SC-A03 전시 정보 입력 | 제목, 소개·주제, 기간·장소, 전시 공통 자료 | artist ID, 해당 전시 작품 |
| 작품 | SC-A04 작품 입력 | 제목·번호·재료 등 식별 정보, 작품 설명·메모, 이미지·근거 | exhibition ID, 소속 작가를 전시로 확인 |
| 원자료·발췌 | A02~A05의 입력/검수 영역 | 파일, 직접 입력 출처, 발췌·페이지·관련 문서 | material ID, 문서 ID·revision, 근거 ID·버전 |

관계는 `작가 → 전시 → 작품`을 기본으로 하고, 작품에서 같은 작가·전시 공통 자료를 참조한다. 계정당 작가 프로필 1개, 전시당 작가 1명을 현재 DB 제약으로 구현했다. 초기 제안은 계정 발급 때 빈 프로필을 준비하는 방식이었으나, 현재 구현은 첫 프로필 조회 또는 첫 전시 생성 시 프로필·빈 문서를 함께 만든다. 계정 생성·로그인·전시 목록 조회만으로 생성하지 않는다. 이름·소개 편집 UI는 후속이며 내용이 비어 있어도 관계 ID는 안정적으로 유지하고 미완성 정보는 게시하지 않는다. 공동전시·작품 원장을 통한 여러 전시 동시 출품은 후속이며 다른 전시 작품 전체를 자동 연결하지 않는다.

현재 초안 API는 기존과 동일한 출처 참조를 보존하고 문서 응답의 `sourceWarnings`로 상위 문서 변경(`source_changed`)이나 문서·자료 이용 불가(`source_unavailable`)를 알린다. 신규·변경 참조는 소유·상위 범위·section·revision 또는 자료 상태를 검증한다. 이는 승인·게시 근거의 검수 흐름을 구현했다는 뜻이 아니다.

작가 홈의 전시 기록은 이 서비스에 등록한 전시의 제목·기간·장소·준비/공개 상태다. 지난 전시도 남기되 종료일이 지났다는 이유로 삭제/중지하지 않는다. 외부 과거 이력을 자동 수집하거나 분석 통계를 만들지 않는다.

# 저장 제안

기존 저장 구조에 `artist_profiles`와 `knowledge_documents`를 추가한다. 작가·전시·작품의 정형 속성은 각 엔티티가 원본이고, 서술 내용과 출처 블록은 해당 `knowledge_documents`가 원본이다. 같은 본문을 여러 테이블에서 독립 편집하지 않는다.

| 필드 | 의미 |
| --- | --- |
| id, owner_id | 불변 문서 ID와 소유자 |
| subject_type, subject_id | artist / exhibition / artwork 중 하나와 실제 엔티티; 소유권·존재 확인 |
| revision, updated_at | 동시 편집·근거 변경 감지용 버전 |
| sections | 안정 section ID, 종류, 입력 본문, 출처 참조. 소개·작품 세계·설명 등을 나눔 |
| source_refs | 직접 입력 또는 material ID·페이지·원본 문서/section·revision |
| related subjects | artist_id·exhibition_id 등 정식 관계에서 조회; 임의 링크가 권한을 만들지 않음 |

입력 폼을 저장할 때 정형 속성과 내부 문서 변경을 함께 반영한다. 실패하면 일부만 성공한 것처럼 표시하지 않는다. 제목·링크 목록 등 AI용 표현은 원본 속성에서 구성할 수 있다. 별도 유료 LLM 호출 없이 폼→문서 블록 정규화로 시작한다. AI 요약/재구성은 기존 해설 초안처럼 후보이며 원자료를 자동 덮어쓰지 않는다.

위키 초안 전체를 관람 검색에 넣지 않는다. 승인 발췌에는 `source_document_id`, `source_section_id`, `source_revision`, 근거 ID·버전·본문·출처·해시를 고정해 공개 묶음에 보존한다. 모든 저장의 전체 이력 UI는 필수가 아니지만 게시에 사용한 근거 버전은 재현 가능해야 한다. 파일은 Storage, 문서와 관계는 DB에 둔다.

# 재사용·승인·철회

1. 작가 공통 정보를 한 번 입력하고 자기 전시에서 연결한다. 연결은 초안 작성 편의이며 공개 승인이 아니다.
2. 전시마다 사용할 section/발췌를 선택·검수하고 공개 묶음에 해당 버전을 고정한다. 이름·소개 등 공개 작가 정보도 전시의 공개 스냅샷으로 관리한다.
3. 작가 원본을 수정하면 새 초안 revision이 된다. 기존 전시의 공개본·해설·음성은 자동으로 바뀌지 않는다. 필요한 전시에서 최신 내용 적용→재검수→게시한다.
4. 단순 수정과 **공개 근거 철회**는 다르다. 철회할 문서 section/근거 버전을 참조하는 모든 자기 전시·작품의 영향을 확인하고 공개 사용을 차단한다. 데이터가 공유되므로 전시 하나만 검사해서 끝내지 않는다. 전시의 공개 소개 자체가 철회된 근거를 사용하면 전시 공개 게이트도 닫아 온보딩·정보 화면에서 이전 소개가 노출되지 않게 한다.
5. 타인 문서, 삭제된 대상, 다른 전시의 작품을 링크로 연결해 접근 범위를 늘리지 않는다. 같은 작가의 다른 전시도 관람객에게 자동 공개하지 않는다.

# AI 검색 경로

[제품 AI 플러그인](product-ai-plugin.md)에 원문 전체 블록을 안정 section으로 분류하고 출처·버전·미변경 section을 보존하는 후보/적용 모듈을 추가했다. 후보 생성은 원본을 변경하지 않으며 작가 검토 후 서버에 저장된 후보 ID로만 적용한다. 실제 후보 DB·원자적 저장 RPC·검수 UI는 후속이다. 일반 폼 저장은 기존 경로를 유지하며 모델 호출이 필수인 것은 아니다.

작가 제작 단계는 소유한 입력과 연결 자료로 **비공개 초안**을 만든다. 관람 단계는 현재 전시·작품의 활성 공개 묶음에서 **승인된 작가 공통 + 전시 공통 + 작품 근거**를 읽는다. 링크를 재귀적으로 따라 전체 작가 위키를 모델에 전달하지 않는다. [제품 RAG](rag-design.md)의 예산·인용·철회 계약을 유지한다.

# 작가가 확인할 정보 — UI 제안

위키 전체를 별도 화면으로 열지 않고 A02~A04에서 원래 입력을 확인·수정한다. A05의 기존 근거 패널에 `작가 공통 / 전시 공통 / 이 작품`, 출처, 사용 버전, 공개 승인 여부를 구분해 표시한다. 정정은 원래 입력 화면으로 이동해 수정하고 필요한 승인을 다시 진행한다.

이는 “작가는 자기 위키를 볼 수 있도록 해야할까?”에 대한 MVP 권고다. 내부 그래프·Markdown 편집기는 후순위다. 작가가 자기 정보조차 확인할 수 없게 숨긴다는 뜻은 아니다. 공개 준비/승인된 근거와 특정 답변이 실제 인용한 근거를 구분하며, 실시간 질문 로그나 전시 전체 관람 분석을 새로 수집하지 않는다.

# 완료 기준

[F-023](../features/F-023-artist-knowledge.md), [UC-17](user-scenarios.md)의 동일 작가 두 전시 재사용·수정·철회·타인 접근을 확인한다. UI는 [SC-A02~A05](screen-spec.md)를 사용한다. DB와 초안 저장·조회·출처 검사 API는 일부 구현했으며 [개발 기반 현황](development-foundation.md)에 실제 검사를 기록한다. 편집 UI·승인/철회·제품 RAG와 전체 관람 시나리오는 미완료다. API·DB 검사 통과가 UC-17 전체 완료를 뜻하지 않는다.


# W10 질문 항목 연결

[작가 질문지 SRC-043](../references/user-artist-questionnaire.md)에 따라 작가 공통 답변 7개를 별도 section으로 보관한다. 같은 이름인 표현 방식/선택 이유도 고유 ID를 사용한다. 기존 작가 bio/practice, 전시 introduction/theme, 작품 description/notes는 보존한다. 전시 기본 선택 3개·작품 세계 선택 6개, 작품 이야기 선택 6개도 해당 주체의 문서에 연결한다.

단일 선언 `src/lib/contracts/knowledge-sections.ts`에서 ID·라벨·질문·필수 여부·길이를 파생한다. 새 카탈로그에 따라 TS와 DB 검증을 함께 확장하며 출처·승인·전시 격리 규칙은 유지한다. 기본 작품 세계 등록 상태는 기존 practice 또는 새 작가 답변 중 비어 있지 않은 항목의 존재를 나타내며, 공개 승인이나 모든 질문 완료를 뜻하지 않는다. 이 절은 W10 진행 설계이고 실제 DB/HTTP 검증 완료 보고가 아니다.
