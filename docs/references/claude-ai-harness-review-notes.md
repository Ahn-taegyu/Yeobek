## 1. 재현한 동작 4건

### 재현 방법

`tests/fixtures/ai.ts`의 `syntheticPublication()`·`syntheticRequest()`와 가짜 제공사로 `createDocentHarness`를 실행하는 임시 단위 테스트를 만들어 관찰했다. 가짜 제공사는 항상 `answered` 응답을 돌려주므로 "모델 호출 수"가 경로를 구분한다. 저장소의 `load`는 fixture 번호(18)가 아닌 번호 조회에 `null`을 반환하게 했다. 임시 테스트는 실행 후 삭제했다. 실제 제공사 호출은 없다.

### 1-1. 승인 해설이 601자 이상이면 그 작품의 모든 질문이 실패

| 입력 | 관찰 |
| --- | --- |
| 승인 해설 600자, 일반 질문 | `answered`, 모델 호출 1회 |
| 승인 해설 601자, 일반 질문 | `HarnessError("invalid_context")`, 모델 호출 0회 |

- 원인: `src/lib/ai/contracts.ts`의 `publicationContextSchema.narration.text`가 `boundedText(AI_LIMITS.answer)`(600)이다. 문맥 검증(`validateContext`)이 해설 요청 여부와 무관하게 먼저 실행되므로 해설이 길면 질문 종류와 상관없이 막힌다.
- 기획: 기능명세 4.1 "해설 글: 600자 이내 목표 유지, 저장·승인 2,000자 상한, 600자 초과는 경고". DB `publications.narration_text`도 2,000자까지 허용한다.
- 관련: 해설 초안(`narration.ts`)도 관람 답변용 `validateAnswer`·`answerJsonSchema`를 빌려 써서 후보가 600자로 제한된다.

### 1-2. 숫자만 보낸 입력이 해설 요청으로 처리되지 않음

| 입력 | 상태 | 관찰 |
| --- | --- | --- |
| `18` | 작품 미선택 | `clarify`, 고정 문구 "어떤 작품인지 번호를 알려 주거나 작품을 선택해 주세요", 모델 호출 0회 |
| `18` | 다른 작품 선택됨 | 선택된 작품에 대한 질문으로 처리, 모델 호출 1회 |
| `18번` | 작품 선택됨 | 18번 작품을 조회하지만 승인 해설이 아닌 모델 생성, 모델 호출 1회 |

- 원인: `src/lib/ai/context.ts`의 `mentionedNumbers`는 `번`이 붙어야 번호로 인식하고, `isNarrationRequest`는 "설명/해설" 표현이 있어야 해설 요청으로 본다. 번호만 있는 입력을 다루는 규칙이 없다.
- 기획: BR-09 "숫자만 전송한 `18`은 `18번 해설 요청`으로 해석한다".

### 1-3. 해설을 청하는 여러 표현이 승인 해설 대신 모델 생성으로 감

| 입력 | 관찰 |
| --- | --- |
| `이 작품 설명해줘` | 승인 해설 반환, 모델 호출 0회 |
| `이 작품에 대해 알려줘` | 모델 생성, 호출 1회 |
| `작품 소개해 주세요` | 모델 생성, 호출 1회 |
| `설명 부탁해요` | 모델 생성, 호출 1회 |
| `해설 들려줘` | 모델 생성, 호출 1회 |

- 원인: `isNarrationRequest`가 `설명|해설` + `해 줘|해 주세요|보기` 꼴만 인정하는 좁은 정규식이다. 요청에 의도를 나타내는 필드가 없어 `해설 보기` 버튼도 문장으로 판별해야 한다.
- 기획: BR-10 "기본 해설은 승인본을 그대로 반환한다".

### 1-4. 질문 속 횟수·지시 표현이 작품 번호로 오해됨

| 입력 | `mentionedNumbers` 결과 | 하네스 관찰 |
| --- | --- | --- |
| `천 번을 봐도 좋네요. 재료가 뭔가요?` | `[1000]` | `HarnessError("publication_unavailable")`, 모델 호출 0회 |
| `이 번에 본 작품 재료는 뭔가요?` | `[2]` | `HarnessError("publication_unavailable")`, 모델 호출 0회 |
| `2024년에 만들었어?` | `[]` | 정상(선택 작품 질문) |
| `한 번 더 설명해줘` | `[]` | 정상 |
| `3번과 5번`, `3번이랑 5번` | `[3, 5]` | 정상(하나를 고르라는 되묻기) |
| `제 3번 질문은` | `[3]` | 3번 작품으로 해석(오판 가능) |

- 원인: `mentionedNumbers`가 한글 수사(일·이·…·천) 뒤에 조사(`을/를/에/도` 등)가 오는 경우도 번호로 인정한다. `이번`은 예외 처리했지만 띄어 쓴 `이 번`은 걸린다.
- 추가 문제: 질문 속 번호로 조회한 작품이 없으면 예외를 던진다. BR-09와 EX-24는 "미존재·비공개 번호는 같은 안내로 처리하고 현재 작품을 유지"다.
- 기획: BR-09 "질문 속 연도·수량을 자동으로 작품 번호로 바꾸지 않는다".

### 참고로 확인한 동작

- 모델 답변에 URL이 있으면 `invalid_output`으로 실패한다. 근거 본문에 URL이 있는 것만으로는 실패하지 않는다. 근거의 주소를 모델이 인용하면 관람객은 오류를 받는다.

## 2. pstack 대응표

비교 기준은 PR 문서(`docs/specs/product-ai-plugin.md`)가 출처로 든 pstack 라우터 스킬 `poteto-mode`다. 이 페이지는 요약 도구로 읽었고 개별 하위 스킬과 플레이북 단계 파일은 읽지 않았다.

| pstack | Yeobek 구현 (`e3c05f0`) | 판정 |
| --- | --- | --- |
| 라우터가 작업에 맞는 플레이북 하나를 고름 | 서버 코드가 업무를 정한다. 관람객 메시지로 업무가 바뀌지 않는다 | 잘 옮김. 제품에서는 모델이 고르게 두면 안 되므로 올바른 변형 |
| 스킬은 이름·설명이 있는 독립 파일 | `ai/yeobek/skills/*/SKILL.md` 5개, 같은 형식 | 잘 옮김 |
| 항상 적용되는 원칙 묶음 | `ai/yeobek/instructions.md` 공통 지침 | 잘 옮김 |
| 플레이북은 순서 있는 단계. 단계를 그대로 할 일 목록에 올리고 건너뛰면 이유를 남김 | `plugin.json`의 플레이북은 스킬 목록과 도구 목록뿐. 실제 순서는 `harness.ts`·`narration.ts` 코드 안에 있음 | 안 옮겨짐 |
| 도구는 에이전트가 실제로 호출하는 것 | 모델은 도구가 없다. `assertPluginTool`은 서버 코드가 자기 상수를 확인하는 이름표 | 이름만 옮김 |
| 대리 지표가 아닌 실물로 검증, 단위마다 확인으로 끝냄 | 모든 검사가 모의 제공사. 실호출 0회 | 안 옮겨짐 |
| 두 번째 모델의 독립 판정 | 해설 초안: Liner 생성 → OpenAI 평가 → 최대 1회 재생성 | 잘 옮김. 해설 경로 한정이고 관람 답변에는 없음 |
| 주장마다 측정·추론·추측을 구분 | 문서가 확정·구현 판단·미검증을 구분. 답변 결과도 `answered`·`clarify`·`insufficient_evidence`로 구분 | 잘 옮김 |
| 스킬을 고칠 때 따르는 플레이북과 평가 플레이북 | 번들 해시 검사와 `ai:compare` 틀은 있으나 실호출·사람 라벨이 없어 스킬 문장 변경의 품질 영향이 검사에 잡히지 않음 | 틀만 옮김 |

### 핵심 차이

- **플레이북에 단계가 없다.** 선언(manifest)과 실행(TypeScript)이 따로 있어, 응답 직전 재확인 같은 단계를 코드에서 지워도 플러그인 쪽에서는 드러나지 않는다.
- **검증이 실물에 닿지 않는다.** 스킬 문장을 바꿨을 때 실패하는 것은 번들 해시 불일치와 특정 문자열을 확인하는 테스트뿐이다.

### 일관성 관점의 구분

- 모델과 무관하게 항상 같은 것: 되묻기·근거 부족의 고정 문구, 승인 해설 재사용, 출력 형식·인용 검사.
- 프롬프트에만 맡긴 것: 관람 답변의 말투와 근거 충실도. `speak-docent`가 지시할 뿐 확인 단계가 없다.
- 스킬처럼 보이지만 설명문인 것: `retrieve-wiki`의 검색 순서. 검색은 서버 코드(`selectEvidence`)가 수행한다.
