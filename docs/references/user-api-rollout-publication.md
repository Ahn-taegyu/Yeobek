# 사용자 확정 요청

> 좋아. 수정 계획을 문서에 반영하고 승인·게시 최소 UI와 cron GET 진입점부터 구현해줘. 유료 API 호출과 원격 설정 변경은 아직 하지 마.

# 요청에 앞서 확인한 수정 계획

- 승인·게시를 초안 저장 → 근거 승인 → 해설 승인 → 게시 조건 확인 → 공개의 한 흐름으로 제공한다. 기본 해설 검수와 질문형 AI 미리보기는 별도 화면이다. 이번 요청은 이 최소 UI에 한해 기존 디자인 누락 기능의 구현 범위를 확장한다.
- 기존 POST 정리 API를 보존하고 동일 인증·처리 로직의 GET 진입점을 추가한다. 실제 스케줄 등록·배포와 원격 환경 변수 변경은 이번 범위가 아니다.
- 실제 글 API 검증과 화면 연결 뒤 음성·가입 메일, 개별 기능 플래그 검증, 전체 흐름 실호출, 스케줄 연결, 마지막으로 미사용 코드 정리 순서로 진행한다. 실호출은 이번에 실행하지 않는다.
- `ai:smoke`에는 qa/draft/judge/tts/stt 등 작업 종류가 필요하다. 각 실행은 제공사 요청 최대 1건이며 생성·평가 모델 계열을 분리한다. 작업 일일 한도는 비용 상한이 아니므로 제공사 사용량과 실제 호출 수를 확인한다.
- 모의 전시를 먼저 중지하고 실제 해설 생성·검수와 활성 작품 전체 재게시를 마친 뒤 운영 트래픽을 연다. 환경 변수 변경만으로 기존 공개본이 숨겨지지 않는다.
- 비교·평가 도구, 제공사 연결, 저장 음성 경로, 기존 계약 스냅샷과 공유 migration 이력을 보존한다. 공개 조회 캐시는 정리 범위에서 제외한다.
- `parallel-work/`와 계획 문서는 보관하고 끝난 일정과 유효한 인계를 구별한다. 루트의 v2/v3 파일 4개는 사용자가 다른 worktree에 둔 미커밋 파일로 현재 main 정리 대상이 아니다.
- Alt·미사용 플래그·대체된 Draft PR·병합 브랜치 정리는 실호출과 필수 흐름 준비 이후 별도 묶음이다. 화면에서 쓰지 않는 API가 모두 비활성이라는 가정은 하지 않는다.

# 이번 구현 경계

문서와 승인·게시 화면, 인증된 정리 GET 및 좁은 회귀를 준비한다. 기존 기능 플래그 기본값·DB·모델·키·원격 설정을 변경하지 않는다. UI 구현과 모의 검증은 실제 메일·모델·음성 품질 또는 운영 스케줄 완료를 뜻하지 않는다.
