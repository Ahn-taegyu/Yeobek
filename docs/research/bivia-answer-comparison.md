# 실험 범위

[후속 요청](../references/user-bivia-answer-recomparison.md)에 따라 **검색뿐 아니라 관람객에게 반환할 최종 답변**을 비교한다. A는 기존 `selectEvidence`, C1은 첫 실험의 Bivia 보류 후순위 정책, C2는 이번 보류 보존 정책이다. A/C2는 동일한 Liner `openai/gpt-6-luna`로 생성하며 별도 계열의 `google/gemini-3.8-flash`가 익명 X/Y 답변을 평가한다. 두 모델 모두 Liner Gateway 경로다. 후속 사용자 승인에 따라 Liner 크레딧을 사용하며, 전체를 무료 실험이라고 표현하지 않는다.

운영 앱과 DB를 변경하지 않는다. 실제 서비스 `createDocentHarness`의 프롬프트·출력 형식·인용/길이 검증·보류 고정 문구를 재사용하되, 합성 publication store의 `isCurrent=true`를 사용한다. 방문 세션 저장·실제 DB 권한/철회·HTTP·최근 대화·음성은 검증 범위가 아니다. 하네스가 선택된 최대12개 근거를 다시 정렬할 수 있으나 제외된 근거를 추가하지 않는다.

# 6,000회와 사용 예산

- 계정 Plan & Usage는 Bivia Requests `6.0K`, `RESETS IN 1 DAY`를 표시했다. **6,000회는 이 계정의 일일 요청 한도**이며 무료 토큰 잔량과 다른 지표다. 정확한 초기화 시각·시간대는 UI에서 확인되지 않았다.
- 첫 실험1,488회는 24.8%다. 개발48회와 평가60문항×24근거=1,440회로 구성됐다. 첫 실험 종료 때 요청 `1.5K/6.0K`, 재확인 때 `0/6.0K`로 표시됐으나 초기화 시점을 추정해 더 쓰지 않았다.
- 실험 직전 무료 토큰 `999M/1.0B`, 90일 만료, 플랫폼 잔액0, 자동 충전은 결제 수단 설정 전 상태를 확인했다. 표시값은 반올림된다. 과거 사용분을 그대로 차감한 잔여4,512회·92,286,528토큰을 로컬 상한으로 유지했다.
- 이전1,440개 점수를 재사용해 60문항의 보류 정책과 답변 품질을 비교한다. 새 Bivia 호출은 개발6문항×24근거×순차/병렬2조건=**288회**뿐이다. 전체 요청·추정 토큰을 실행 전에 예약하고 실패·중단 시 자동 환급하지 않는다.
- Liner는 사용자 승인 크레딧으로 생성120회·최초 평가60회를 실행한다. 평가 입력의 작품 메타데이터 누락을 바로잡아 같은 답변60쌍을 추가60회 평가하며, 두 실행을 합산한 공시 토큰 단가 기반 예약 상한 $3를 유지한다. 단가 환산은 청구서나 실제 현금 결제액이 아니다. 결제 설정·충전은 변경하지 않는다.

# 변경한 동작과 재현 조건

1. Bivia 요청은 동시에 최대4개다. 요청 직전 동기적으로 한도를 차감한다. 오류가 관측되면 새 요청을 중단하고 이미 전송된 요청의 완료를 기다려 사용량을 집계한다. 자동 재시도·유료 대체·A로의 숨은 장애 전환은 없다.
2. C2는 **A가 선택했던 근거 중 Bivia가 보류한 근거를 먼저 보존**하고 남은 예산을 Bivia 점수 순서로 채운다. 보류를 무관함으로 단정하지 않으며 점수나 확률을 임의로 보정하지 않는다. 점수와 선택된 출처 버전·본문은 보존한다. 모든 후보 보류 시 A 선택을 재현한다. 최대12개·8,000 코드 포인트·원문 단위 예산은 그대로다.
3. 캐시는 첫 공개 집계의 원본 SHA-256, 전체 corpus hash, scoring prompt hash, 완료 상태, 문항/근거의 중복·누락을 모두 검사한 뒤 사용한다. corpus·질문·버전·본문 변경은 캐시 재사용을 차단한다. 이번 비교에서 scoring prompt와 corpus는 변경하지 않았다.
4. 속도는 개발 데이터의 유형별 첫1문항, 총6문항에서 동시성1/4를 교대 순서로 실행한다. 두 조건 모두 C2 정책이다. 서버 부하·점수 변동이 있는 작은 표본이며 C2의 60문항 전체 지연으로 확대해 해석하지 않는다.
5. 답변은 기존 평가60문항에서 각 안1회, 총120개다. A/C2 생성 순서와 X/Y 평가 노출 순서를 별도로 교대한다. 생성에는 정답을 주지 않으며 평가에는 기대 사실·실제 인용 본문을 준다. 평가 기준은 사실 근거, 완전성, 적절한 답변/보류, 인용의 의미 일치, 한국어 명료성이다. 실제 JSON·인용 ID·outcome 검증 실패는 별도 실패로 센다.
6. 이 60문항은 첫 검색 실험에서 이미 본 **합성 회귀 세트**다. 새 독립 잠금 세트나 사람 수용 평가가 아니다. 보류 정책을 재평가 결과에 맞춰 반복 조정하지 않았다. C1의 최종 답변은 생성하지 않아 C1→C2의 답변 개선을 주장할 수 없다.

# 실행 명령과 키

필요한 키는 `BIVIA_API_KEY`, `LINER_API_KEY`다. Gemini/Groq 직접 키는 이번 Liner 실행에 필요하지 않다. 현재 worktree의 `.env.local`에만 서버 키를 두며 다른 작업 공간의 DB·배포 설정을 복제하지 않는다. 로컬 앱의 `AI_PROVIDER_MODE=mock`을 유지하고 이 실험 CLI만 명시적으로 호출한다.

```sh
# 최초 실험의 비공개 report.json을 지정. 공개 집계에 고정된 해시와 일치해야 함.
# BIVIA_SCORE_CACHE 환경변수 또는 .ai-eval/bivia-score-cache.json 사용
npm run ai:recompare:bivia -- --mode=replay

# 최근 계정 UI 확인 후 기존 .ai-eval/bivia-free-allowance.json 사용
npm run ai:recompare:bivia -- --mode=benchmark-free

# 사용자에게 Liner 크레딧 사용 권한을 받은 터미널에서만
# BIVIA_LINER_CREDIT_AUTHORIZED=1 설정 후 실행
npm run ai:recompare:bivia -- --mode=answers-credit

# 평가기 입력을 수정한 경우에만: BIVIA_ANSWER_REPORT에 완료된 원본 report.json 지정
# 새 답변 없이 고정된 60쌍 전체를 동일 평가 조건으로 재검사
npm run ai:recompare:bivia -- --mode=judge-credit
```

공개 저장소에는 집계와 원본 해시만 있다. 동일한 비공개 점수 보고서가 없는 복제본에서는 캐시 재평가가 차단된다. 새 실측 결과를 쓰려면 별도 실험으로 원본·manifest를 검토하여 고정해야 하며 임의 점수나 가짜 응답으로 대체하지 않는다.

`replay`는 외부 fetch를 차단한다. 나머지 명시적 live 모드는 자격 증명을 읽는다. `answers-credit`는 `.ai-eval/bivia-answer-reservation.json`을 배타적으로 생성하여 같은 작업의 실수 재실행을 막는다. 파일을 자동 삭제하지 않는다. 중단된 작업은 보고서·이미 사용한 호출 수를 확인하고 다음 실행 범위와 예산을 다시 정한 뒤 처리한다. `judge-credit`도 별도의 배타적 예약 파일을 만들며 원 실행의 비용 예약을 차감한 잔여 상한만 사용한다. 최초 재평가는 동시에 최대3쌍이며 오류 시 진행 중 요청을 정산한 뒤 멈춘다. 시간 초과 후 수동 재개는 `BIVIA_JUDGE_RESUME`에 중단 보고서를 명시한다. 원본 답변·평가 프롬프트·모델·완료 행의 일치를 검증하고 성공한 평가를 보존한 채 미완료 쌍만 최대2개씩 실행한다. 이전 실패 요청의 사용량을0으로 가정하거나 비용 예약을 환급하지 않으며, 같은 체크포인트를 중복 재개할 수 없다. 자동 재시도와 수동 복구 횟수는 구분해서 기록한다. 원본 응답·키·계정 식별자는 공개 Git에 올리지 않는다. 정규 CI는 오프라인 단위 검사만 실행하며 이 live 실험을 발견하지 않는다.

최종 집계는 완료된 결과에 대해서만 다음 오프라인 명령으로 내보낸다. 답변 전문·원문·계정 정보는 허용 목록에 없으며 집계 파일에 포함되지 않는다.

```sh
node scripts/bivia-summary.mjs --benchmark=벤치마크/report.json --answers=최종평가/report.json --output=tests/evaluation/results/bivia-answer-comparison-2026-11-14.json
```

## 평가기 보정과 오류 기록

첫60쌍 평가에서 작품 metadata를 전달하지 않아 올바른 작품명 `창문 없는 숲`을 근거 없는 표현으로 감점한 사례를 발견했다. 평가 입력에 생성기가 받았던 제목·번호를 추가하고 **120개 답변을 바꾸지 않은 채 전체60쌍을 같은 수정 평가기로 다시 평가**했다. 최초 평가를 최종 품질 집계와 섞지 않는다.

재평가의 첫 시도는 동시성3에서15회 호출 후1회 `timeout`으로 중단됐다. 성공14건을 보존하고 원본 답변·평가 프롬프트·모델 해시를 대조한 뒤, 남은46쌍만 동시성2로 수동 재개했다. timeout은 사용량 미확인1회로 남겨 비용 예약을 유지한다. 자동 재시도0회이며 이미 성공한 답변 생성이나 Bivia 판단을 다시 호출하지 않았다.

## 최종 답변

[공개 집계 JSON](https://github.com/Docendocen/Yeobek/blob/test/bivia-retrieval-comparison/tests/evaluation/results/bivia-answer-comparison-2026-11-14.json)에 원본 보고서 SHA-256, 실제 실행 코드 SHA·파일 해시, 모델·프롬프트, 문항별 결과와 사용량을 기록했다. 생성은 최초 실행의 코드·프롬프트, 최종 평가는 `e9ac316` 코드 기준이며 원본 생성 provenance를 별도 보존한다.

| 최종 답변 지표 | A 기존 검색 | C2 Bivia 보완안 |
| --- | --- | --- |
| 모든 품질 항목 통과 | 56/60 (93.3%) | 59/60 (98.3%) |
| 답이 있는 질문에서 통과 | 46/50 (92%) | 49/50 (98%) |
| 답 없는 질문의 적절한 보류 | 10/10 | 10/10 |
| 서비스 출력·인용 ID 검증 | 60/60 | 60/60 |
| 생성+로컬 하네스 검증 p50 | 2.120초 | 2.527초 |
| 생성+로컬 하네스 검증 p95 | 4.557초 | 4.655초 |

마지막 두 행은 **Bivia 점수를 캐시에서 사용한 답변 생성 단계**다. 실시간 Bivia 검색까지 합친 전체 응답 지연이 아니며, 6문항 검색 p95와 60문항 생성 p95를 더해 전체 p95라고 쓰지 않는다.

문항별로 개선4·악화1·동률55, 전체 통과율 차이는 +5%p다. 개선은 `eval-6-table`의 제작 연도, `eval-7-multi`·`eval-9-multi`·`eval-12-multi`의 의도/과정 복수 근거였다. 악화는 `eval-6-touch`의 접촉 금지 안내 누락이다. 원본과 최종 보고서의120개 답변이 전부 동일함을 대조했고, 실패 사례·보류10문항과 여러 성공 답변을 생성 입력/출처와 직접 검토했다. 이것은 에이전트의 추가 검토이며 독립적인 사람 평가가 아니다.

- `eval-6-touch`: A는 접촉 금지를 명확히 안내했다. C2는 접촉 가능 여부를 확인할 수 없다고 말하고 안전선 안내만 추가했다. JSON과 인용 ID가 유효해도 핵심 관람 규칙을 전달하지 못했다. 자동 평가의 통과율 평균으로 이 실패를 상쇄하지 않는다.
- `eval-8-paraphrase`: A는 정답표에 지정된 재료표 ID를 놓쳤지만 제작 과정에 포함된 같은 재료로 올바르게 답했다. 그래서 A의 엄격한 근거 그룹 회수45/50과 답변 통과46/50은 다르다. 이전 정답 근거를 소급 수정하지 않고 두 지표의 의미 차이를 기록했다.
- 평가기의 grounded/인용 항목은 검색에서 빠진 사실을 답변에서 확인할 수 없다고 한 경우에도 감점할 수 있다. 이 항목의 실패 수를 그대로 환각 수나 고의로 지어낸 작가 의도 수로 해석하지 않는다.
- 작품8개 단위로 질문 쌍을 묶어10,000회 재표집한 참고95% 구간은 +1.56~+10.0%p다(seed20261114). 이미 관찰한 합성 작품·공통 질문 템플릿·1회 생성·자동 평가라는 한계가 있어 실제 전시의 일반화 근거로 사용할 수 없다.

## 사용량과 정상 요율 환산

| 항목 | 이번 추가 실행 | 비용 해석 |
| --- | --- | --- |
| Bivia | 288회, billable tokens288,000, 사용량 미확인0 | 확인한 무료 할당량 사용, 유료 호출0 |
| Liner 답변 생성 | 120회 | 사용자 승인 크레딧 경로 |
| Liner 평가 | 최초60회 + 보정61회 =121회 | 보정 성공60회와 timeout1회 포함 |
| Liner 확인된 합계 | 입력281,421·출력64,838토큰 | 공시 단가 환산 **$0.28150**, timeout1회 사용량 제외 |
| Liner 보수적 비용 예약 | 합산$2.66826 / 상한$3 | 실패 요청 예약을 포함하며 실제 청구액은 아님 |

Bivia 실험 누적은 이전1,488회+이번288회=**1,776회**다. 정확한 일일 초기화 시각을 추정하지 않고 과거분까지 차감한 로컬 잔여4,224회를 유지했다. 실험 후 계정 UI는 요청288/6,000·무료 토큰998M/1.0B·플랫폼 크레딧 사용0을 표시했다. 무료 토큰 표시는 반올림값이다.

Liner 단가는 입력/출력100만 토큰당 생성 모델$0.10/$0.50, 평가 모델$0.825/$4.125를 적용했다([공식 Gateway](https://liner.com/ko/developers/docs/llm-gateway), 확인2026-11-14). 지원 크레딧 차감과 실제 현금 결제 내역은 별도이며 토큰 환산을 청구서로 제시하지 않는다.

평가 호출을 제외한 질문당 생성 환산액은 A약$0.000248, C2약$0.000253이다. 무료 혜택 종료를 가정하고 후보24개×1,000 billable tokens에 Bivia 공시$0.042/100만 토큰을 적용하면 검색약$0.001008이 추가되어 C2총약$0.001261, A의약5.09배다. **현재 청구 비용이 아니라 이번 크기의 후보와 공시 요율을 사용한 추산**이다. 문서 준비·저장·재처리 비용은 제외했다.

## 판단과 후속 범위

**현재 운영 검색은 A를 유지하는 것이 타당하다.** 최대4개 병렬화의 속도 개선은 확인됐지만, C2는 접촉 금지 안내를 놓쳤고 품질 개선+5%p·근거 회수+8%p는 P-006의 잠정10%p 기준에 미달했다. 무료 혜택 이후의 질문당 비용 추산도1.2배 기준을 넘는다. 실제 전체 응답 지연의1.2배 기준은 이번 캐시 기반 생성 실험으로 검증하지 못했다.

보류 자료를 무조건 선점시키면 중요한 답변 근거가 밀릴 수 있으므로, 후보 축소와 검색/보류 우선순위 정책을 개발 세트에서 다시 설계할 여지가 있다. 다음 평가에는 새 독립 문항·사람의 정답/관람 안전 규칙 검수·3회 반복·실제 DB 권한/철회·전체 경로 지연을 포함한다. 이번 실험에서 운영 RAG·DB·Numa 채택을 완료한 것은 아니다.

## 검사와 인계

관련 좁은 단위 검사34개 및 수정한 평가 metadata/비용 경계의 재검사를 통과했다. 실제 API 실험은 Bivia288회, Liner241회(사용량 미확인 timeout1회 포함)다. 원본 답변 동결, 집계의 품질 통과 수56/59 및 근거 ID 회수45/49/49를 별도 코드로 재집계해 일치함을 확인했다. 변경 파일 lint·문서 check·diff 검사와 비밀값 제외 검사를 수행했다. 전체 문서 verify와 앱 회귀는 최신 [PR #40 CI](https://github.com/Docendocen/Yeobek/pull/40/checks)를 따른다. 정규 CI에서 외부 모델은 호출하지 않는다.
