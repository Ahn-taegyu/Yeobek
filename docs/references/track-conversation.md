## 1. 공식 안내에서 확인되는 대회의 방향

공식 모집 페이지에는 다음 내용이 나옵니다.

- 참가자가 **1인이 운영할 수 있는 AI 자동화 프로그램을 직접 설계하고 구현**한다.
- 트랙 2에서는 **파트너 기업의 API 또는 데이터를 핵심 엔진으로 활용하는 AI 자동화 SaaS**를 구축한다.
- 제품뿐 아니라 마케팅 전략과 시장 검증 등을 준비하고, MVP 완성도·시장 반응·가상 투자 결과 등을 함께 평가한다. :chatgpt-content-reference{index="0"}

이 내용을 종합하면, 저는 대회가 요구하는 핵심을 **“고객에게 가치를 제공하고, 그 사업을 한 명이 반복해서 운영할 수 있는 구조를 실제로 보여주는 것”**으로 해석합니다.

다만 공개 문구만으로는 ‘1인’이 반드시 서비스 공급 회사를 뜻하는지, 고객인 1인 사업자를 뜻하는지까지 확정할 수 없습니다. 따라서 **1번만 인정되고 2번은 부적합하다는 판정은 아닙니다.** 아래 비교는 공개 안내를 바탕으로 한 제 전략적 판단입니다.

## 2. 두 방안은 서로 다른 문제를 설명하고 있습니다

두 방안의 가장 큰 차이는 **누구의 일을 자동화하느냐**입니다.

| 비교 항목 | 1번: AI 도슨트 공급 회사를 1인 운영 | 2번: 작가·미술관의 업무 자동화 제공 |
|---|---|---|
| 핵심 질문 | 우리 회사가 여러 고객에게 서비스를 혼자 제공할 수 있는가? | 고객이 전시와 관련된 업무를 더 적은 수고로 처리할 수 있는가? |
| 자동화 대상 | 고객 접수, 자료 정리, 도슨트 제작, 배포, 고객 지원 등 | 작품 설명, 관람객 응대, 문의 처리, 후속 안내 등 |
| 대회 주제와의 연결 | **1인 회사의 운영 가능성을 직접 설명하기 좋음** | 고객의 업무가 실제로 줄어드는 효과를 보여주기 좋음 |
| 기존 아이디어와의 연결 | 기존 도슨트 사업을 유지하면서 제공 과정을 개선 | 도슨트를 중심으로 고객에게 제공하는 기능을 확장 |
| 주의할 점 | 실제 도슨트 제작은 수작업인데 주변 업무만 자동화할 수 있음 | 전시 운영 전반으로 범위가 넓어져 핵심 기능이 흐려질 수 있음 |
| 제 추천 | **출품 사업의 기본 구조로 채택** | **도슨트와 이어지는 업무로 범위를 좁혀 채택** |

### 1번이 더 직접적으로 맞지만, 자동화의 위치가 중요합니다

예를 들어 다음과 같은 구성이라면 1번의 설득력이 약합니다.

- 작가 인터뷰는 팀원이 매번 진행한다.
- 인터뷰 내용을 팀원이 정리하고 작품별 설명을 작성한다.
- 개발자가 작가마다 챗봇과 전시 페이지를 따로 만든다.
- 회사 소개 이메일과 일정 관리만 자동화한다.

이렇게 하면 고객이 늘어날 때마다 핵심 제작 업무도 함께 늘어납니다. **한 명이 사업을 운영할 수 있다는 주장을 뒷받침하려면, 도슨트를 제공하는 핵심 과정의 수작업을 줄여야 합니다.**

반대로 작가가 직접 자료를 등록하고, 같은 절차로 도슨트를 생성·게시하고, 운영자는 오류나 특수 요청을 처리하는 구조라면 1번의 의미가 명확해집니다.

### 2번도 충분히 맞지만, ‘작가·미술관의 모든 업무’는 넓습니다

2번을 다음처럼 잡으면 기존 아이디어와 잘 이어집니다.

> 작가가 한 번 설명한 내용을 활용해 전시 안내를 만들고, 관람객 질문에 응답하고, 추가 설명이 필요한 부분을 다시 작가에게 전달한다.

반면 여기에 예약, 회계, 작품 판매, 배송, 재고, 홍보, 공간 관리까지 넣으면 풀어야 할 문제가 크게 늘어납니다. 이번 해커톤에서는 구현 범위가 커지고, **왜 AI 도슨트에서 출발했는지 설명하기 어려워질 가능성**이 있습니다.

미술관을 고객으로 삼는 것 자체가 대회 취지에 어긋난다는 뜻은 아닙니다. 다만 초기 고객을 **직접 전시를 준비하는 작가 또는 소규모 전시 공간 운영자**로 좁히면, 어떤 일을 줄여주는지 더 구체적으로 보여줄 수 있습니다.

## 3. 추천하는 방식: 도슨트 제공 과정을 하나의 자동화 흐름으로 만들기

제가 추천하는 제품의 중심은 **‘작가가 스스로 개설하고 운영하는 AI 도슨트’**입니다.

이 구조에서는 역할을 다음처럼 구분하면 좋습니다.

- **우리 회사:** 한 명이 여러 전시에 도슨트 서비스를 제공하는 사업자
- **유료 고객:** 작가 또는 전시 운영자
- **최종 사용자:** 작품에 관해 질문하는 관람객

그리고 고객이 들어온 뒤 서비스가 제공되는 과정을 아래처럼 연결합니다.

| 단계 | 제안하는 제품 동작 | 줄어드는 업무 |
|---|---|---|
| ① 자료 입력 | 작가가 작품 이미지·기본 정보를 넣고, 질문지에 따라 작품 이야기를 녹음하거나 작성 | 공급 회사가 매번 자료를 요청하고 인터뷰하는 작업 |
| ② 자료 정리 | 작가의 이력, 작품 의도, 재료, 표현 방식 등을 작품별로 정리하고 설명 초안 생성 | 인터뷰 전사문을 읽고 도슨트 자료로 편집하는 작업 |
| ③ 작가 확인 | 작가가 잘못된 내용과 공개하고 싶지 않은 부분을 수정하고 승인 | 공급 회사와 여러 차례 자료를 주고받는 작업 |
| ④ 전시 게시 | 승인된 자료로 전시 페이지와 작품별 QR 생성 | 작가별 페이지와 챗봇을 따로 만드는 작업 |
| ⑤ 관람객 응대 | 승인된 자료를 근거로 질문에 답하고, 자료에 없는 질문은 기록 | 작가의 반복 설명과 공급 회사의 개별 응답 관리 |
| ⑥ 운영 개선 | 자주 나온 질문과 답하지 못한 질문을 정리해 작가에게 전달 | 관람객 질문을 직접 모으고 보완할 내용을 찾는 작업 |

**이 흐름 하나가 두 방안을 동시에 충족합니다.**

작가는 작품 설명과 관람객 응대에 드는 수고를 줄이고, 우리 회사는 자료 정리·도슨트 제작·배포에 드는 수고를 줄입니다. 내부 업무 자동화 시스템과 고객용 자동화 시스템을 각각 크게 만들 필요가 없습니다.

여기서 작가의 확인 단계는 남기는 것이 좋습니다. 작품에 담긴 의도와 감정은 작가가 제공하는 핵심 정보이므로, **자동화할 부분은 정리와 전달이며 최종 내용의 확인은 작가가 맡는 구조**가 자연스럽습니다.

또한 앞서 공유하신 작가 피드백의 “관람객에게 일일이 설명해 주고 싶지만 그러지 못한다”는 문제와도 직접 연결됩니다. 기존에 확인한 문제를 유지하면서, 그 문제를 해결하는 서비스의 제공 방식까지 구체화하는 방향입니다.

## 4. 제공 도구들은 이렇게 연결하면 자연스럽습니다

공식 공개 개발자 문서를 기준으로 확인한 기능과, 이를 여러분의 서비스에 적용하는 제안을 구분하면 다음과 같습니다.

| 도구 | 공개 문서에서 확인한 기능 | AI 도슨트에 적용할 방식 |
|---|---|---|
| **Alt** | 기존 노트·전사문·요약문을 API로 읽고, 녹음 종료·요약 완료 등의 알림을 받아 후속 작업 실행 | 작가가 녹음한 작품 설명을 가져와 도슨트 자료로 정리하는 시작점. :chatgpt-content-reference{index="1"} |
| **라이너** | 메시지를 입력받아 답변을 생성하는 LLM API와 웹·학술 검색 API 제공 | 작가 자료를 입력에 포함해 설명·답변을 생성하고, 필요한 경우 외부 미술 지식을 검색하는 기능. :chatgpt-content-reference{index="2"} |
| **스티비** | 구독자 추가·그룹 관리, 이메일 생성·발송·성과 조회 등의 API 제공 | 구독에 동의한 관람객에게 전시 후 작품 이야기나 다음 전시 소식을 보내는 후속 안내. :chatgpt-content-reference{index="3"} |
| **채널톡** | 외부 서비스와 데이터를 주고받는 앱 및 커맨드 연동 | 작가의 수정 요청이나 서비스 문의를 접수하고, 전시 상태 조회 등 우리 서비스의 기능과 연결. :chatgpt-content-reference{index="4"} |

이 가운데 **Alt를 통한 자료 입력과 라이너를 통한 자료 정리·답변 생성이 핵심 제공 과정에 가깝고**, 스티비와 채널톡은 고객 관계와 운영을 이어주는 역할로 배치할 수 있습니다.

### 라이너 활용에서는 작가 자료와 외부 지식의 역할을 구분해야 합니다

여러분의 원래 아이디어는 작가가 자신의 역사, 작품 세계, 표현 방식, 창작 당시의 생각과 감정을 제공하는 방식입니다. 이 정보가 도슨트의 중심이어야 합니다.

예를 들어 다음 두 질문은 필요한 근거가 다릅니다.

- **“작가가 이 작품에서 파란색을 사용한 이유는 무엇인가요?”**  
  작가가 제공하고 승인한 자료를 근거로 답해야 합니다.

- **“이 표현 기법은 미술사에서 어떻게 사용되었나요?”**  
  외부 자료를 검색하고 출처를 제시하는 기능을 활용할 수 있습니다.

현재 공개된 라이너 문서에는 일반 LLM 응답 API도 있으므로, 작가 자료를 입력에 포함하는 구현을 검토할 수 있습니다. 다만 **작가 자료 저장, 작품별 연결, 답변 근거 관리는 우리 서비스에서 설계할 부분**입니다. 라이너의 검색 API만 연결하면 작가 전용 도슨트가 완성된다고 전제해서는 안 됩니다. :chatgpt-content-reference{index="5"}

또한 Alt는 이번에 확인한 문서상 **Alt에서 생성된 전사·요약을 API로 가져오는 방식**이 명확합니다. 우리 웹페이지에 음성 파일을 올리면 Alt API가 곧바로 전사해 주는 기능까지 확인한 것은 아닙니다. :chatgpt-content-reference{index="6"}

**기술 구성을 확정하기 전에 확인할 사항은 두 가지입니다.** 행사에서 네 도구를 모두 사용해야 하는지, 그리고 제공되는 키·크레딧으로 어떤 API까지 이용할 수 있는지입니다. 문자에 있는 행사 전용 라이너 Notion과 Alt 발표자료는 제가 본문을 확인하지 못했으므로, 위 구성은 공개 개발자 문서 기준의 제안입니다.

## 5. 해커톤에서는 이 정도로 좁혀 시연하는 것을 추천합니다

저라면 **작가 한 명, 전시 한 개, 작품 세 점 정도**를 기준으로 다음 세 화면을 만들겠습니다. 이는 구현 범위를 잡기 위한 제안입니다.

### ① 작가용 등록·확인 화면

작품 정보와 녹음·설명 자료를 넣으면 작품별 설명 초안이 생성되고, 작가가 수정한 뒤 게시할 수 있게 합니다.

여기서 보여줄 가치는 **자료가 들어온 뒤 공급 회사의 별도 편집 작업 없이 도슨트 준비가 진행되는 것**입니다.

### ② 관람객용 도슨트 화면

작품 QR로 접속해 질문하고, 답변의 근거가 된 작가 설명을 확인할 수 있게 합니다.

시연에서는 자료로 답할 수 있는 질문과 자료에 없는 질문을 각각 하나씩 보여주면 좋습니다. 자료에 없는 내용은 작가의 의도를 임의로 만들어 답하지 않고, 추가 설명이 필요한 질문으로 남깁니다.

### ③ 운영 결과 화면

어떤 작품에 어떤 질문이 들어왔는지, 답하지 못한 질문은 무엇인지, 작가에게 어떤 정보를 보완받아야 하는지 보여줍니다.

여기까지 구현하면 **입력 → 제작 → 게시 → 이용 → 개선**이 연결됩니다. 이후 여력이 있으면 스티비 후속 안내나 채널톡 문의 연계를 붙이는 순서가 좋겠습니다. 네 도구 사용이 필수로 확인된다면, 같은 흐름 안에서 각 도구가 맡을 최소 기능을 정하면 됩니다.

특히 가능하다면 **두 번째 전시도 같은 절차로 만들어지는 장면**을 보여주세요. 첫 전시를 위해 개발자가 수동으로 내용을 세팅한 것인지, 새로운 고객이 들어와도 반복해서 사용할 수 있는 제품인지가 훨씬 분명해집니다.

### ‘1인 운영 가능성’은 다음 지표로 설명할 수 있습니다

- 새 전시 하나를 게시하기까지 **공급 회사 사람이 실제로 작업한 시간**
- 작가가 자료를 입력하고 확인하는 데 걸린 시간
- 새로운 작가가 들어왔을 때 별도 개발·수정이 필요한지
- 자동으로 처리된 질문과 사람이 추가로 확인해야 한 질문
- 전시 한 건을 운영하는 데 발생한 API 비용

이 수치를 실제 시연에서 측정하면 “한 명이 운영할 수 있다”는 설명에 근거가 생깁니다. 측정 전에는 목표로 제시하고, 검증된 성과처럼 표현하지 않는 편이 좋습니다.

## 6. 대회 적합성과 별개로, 아직 검증해야 할 사업 가설은 있습니다

**현재 확보한 작가 피드백은 작품 설명을 제공하고 싶다는 수요의 초기 근거**로 볼 수 있습니다. 다만 그 피드백만으로 다음까지 확인됐다고 보기는 어렵습니다.

- 작가가 직접 자료를 입력하고 도슨트를 만들 의향이 있는가?
- 관람객이 실제로 QR을 열고 질문하는가?
- 작가 또는 전시 운영자가 이용료를 지불할 의향이 있는가?
- 작품 설명 외에 홍보·문의 관리까지 함께 자동화하기를 원하는가?

따라서 2번의 범위를 넓히기 전에, 기존에 피드백을 준 작가에게 실제 작품을 넣은 데모를 보여주고 **입력 부담, 설명의 정확성, 실제 전시 도입 의향**을 확인하는 것이 유용합니다. 가격도 막연히 “돈을 낼 것 같다”는 답을 받기보다, 전시 한 회에 사용하는 상품을 가정해 반응을 확인할 수 있습니다.

공식 안내가 시장 반응도 평가한다고 밝히고 있는 만큼, 이러한 실제 반응을 제시하는 것은 대회 방향과도 연결됩니다. :chatgpt-content-reference{index="7"}

---

제가 팀의 방향을 정한다면 **“1인이 운영하는, 작가용 AI 도슨트 제작·운영 SaaS”**로 정하겠습니다.

1번의 회사 운영 구조를 중심에 두고, 2번에서 **자료 입력·작품 설명·관람객 응대·운영 피드백**만 가져오는 것입니다. 이 정도면 기존 AI 도슨트의 핵심 가치를 유지하면서도 자동화가 사업의 중요한 부분을 담당하게 됩니다.

발표에서는 다음 문장이 여러분의 의도를 잘 전달할 것 같습니다.

> **“작가가 자신의 작품 이야기를 한 번 정리하면, 전시용 AI 도슨트 제작부터 관람객 응대와 질문 분석까지 이어지는 서비스를 만듭니다. 신규 전시를 개설하고 운영하는 과정을 자동화해, 한 명이 여러 작가의 전시를 지원할 수 있도록 설계했습니다.”**

## User

전시 단위로 자동화 해주는 것도 적용될까? 입장료 수익이나 작품 판매로 이어지는 절차를 모두 자동화 하는 과정에서 AI 도슨트가 필요할 테니까

## Assistant

**네. “작가나 기획자 한 명이 전시라는 사업을 운영하도록 자동화한다”는 구성이면, One-Person AI Company의 범주에 충분히 들어간다고 봅니다.**

핵심은 **전시 자체를 회사라고 부르는 데 있지 않고, 전시를 통해 수익을 내는 사업자가 혼자 운영할 수 있는 구조를 만드는 데 있습니다.** 지금 말씀하신 방향은 앞서의 2번을 훨씬 구체적으로 만든 것이어서, 이 방향을 제품의 중심으로 잡아도 좋겠습니다.

다만 이것은 공식 안내를 바탕으로 한 제 판단입니다. 공개 모집글은 ‘1인이 운영 가능한 AI 자동화 프로그램’과 ‘파트너 API·데이터를 핵심으로 활용하는 자동화 SaaS’를 요구하고 있지만, 전시 사업의 포함 여부나 ‘1인’이 공급 회사와 고객 중 누구를 가리키는지까지 명시하지는 않습니다. 

## 1. 전시는 ‘사업을 수행하는 단위’로 보면 됩니다

프리랜서 디자이너가 프로젝트마다 수익을 얻는다고 생각하면 이해하기 쉽습니다. **프로젝트 한 건이 회사 자체는 아니지만, 그 프로젝트를 수주하고 수행하는 사람은 1인 사업을 운영할 수 있습니다.**

전시도 같은 논리로 설명할 수 있습니다.

- **사업 운영자:** 작가 또는 독립 전시 기획자
- **제공하는 상품·서비스:** 전시 관람 경험과 작품
- **고객:** 관람객과 작품 구매자
- **수익:** 입장료, 작품 판매 등
- **반복되는 운영 업무:** 전시 소개, 예약, 관람 안내, 작품 설명, 구매 문의, 주문 관리, 후속 연락

따라서 **‘전시 단위로 운영한다’는 점은 One-Person Company와 충돌하지 않습니다.** 오히려 전시라는 단위가 있으면 자동화가 어디에서 시작해서 어디까지 이어지는지 구체적으로 보여줄 수 있습니다.

다음 세 설명은 대회 취지를 전달하는 힘이 다릅니다.

| 설명 | 전달되는 의미 |
|---|---|
| “이번 전시에 도슨트와 예매 기능을 붙였습니다.” | 특정 전시에 필요한 기능을 개발했다는 설명 |
| “작가 한 명이 전시를 열고 관람객 응대와 판매 관리를 할 수 있게 했습니다.” | **1인 사업자의 운영을 자동화했다는 설명** |
| “작품과 전시 정보를 등록하면 같은 절차로 전시 개설·응대·거래 관리를 시작할 수 있습니다.” | **그 운영 방식을 반복해서 사용할 수 있는 SaaS로 만들었다는 설명** |

저라면 두 번째를 문제 정의로, 세 번째를 제품 설명으로 사용하겠습니다.

## 2. 입장료와 작품 판매가 있으면 ‘사업’의 구조를 설명하기도 좋아집니다

말씀하신 접근의 장점은 **도슨트가 들어갈 실제 사업 과정이 생긴다는 것**입니다.

전시를 운영하는 사람이 해야 할 일을 따라가면 다음과 같은 흐름을 설계할 수 있습니다.

> 전시 개설 → 관람객 유치 → 예약·예매 → 관람 안내 → 작품 이해 → 구매 문의·주문 → 후속 관리

이 가운데 어느 업무가 자동으로 처리되고, 운영자에게 어떤 판단만 남는지 보여주면 됩니다. 그러면 “AI를 사용한 전시 서비스”에서 더 나아가 **“한 사람이 전시 사업을 운영할 수 있도록 만든 시스템”**이라는 설명이 가능합니다.

여기서 사업 구조를 한 번 더 구분해 두면 발표가 명확해집니다.

| 구분 | 사업 주체 | 매출의 예 |
|---|---|---|
| **전시 사업** | 서비스를 사용하는 작가·기획자 | 입장료, 작품 판매 대금 |
| **여러분의 SaaS 사업** | 전시 자동화 서비스를 제공하는 회사 | 전시별 이용료, 구독료 등 |

즉, **고객의 전시 매출과 여러분 회사의 매출은 구분해서 설명해야 합니다.** 여러분은 고객이 혼자 전시 사업을 운영할 수 있도록 돕고, 그 서비스의 대가를 받는 구조입니다.

또한 고객이 직접 전시를 개설하는 방식으로 만들면, 여러분 회사의 고객별 제작 업무도 줄어듭니다. 이 경우 고객의 1인 사업 운영과 공급 회사의 1인 운영 가능성을 함께 보여줄 수 있습니다.

## 3. 다만 “수익화에 AI 도슨트가 필요하다”는 연결은 구체화해야 합니다

여기에는 한 가지 짚을 부분이 있습니다. **입장권이나 작품을 판매하는 절차 자체는 도슨트 없이도 자동화할 수 있습니다.** 따라서 도슨트가 어떤 문제를 해결해서 수익 흐름에 기여하는지를 설명해야 합니다.

두 수익 모델에서 도슨트가 기여하는 위치도 다릅니다.

| 수익 모델 | 도슨트가 맡을 수 있는 역할 | 설명할 때 주의할 점 |
|---|---|---|
| **입장료 수익** | 방문 전 전시 소개, 작품 일부에 대한 사전 질의응답, 관람 여부 판단 지원 | 현장에서만 사용하는 도슨트는 이미 구입한 입장권의 첫 구매를 설명하기 어려움 |
| **작품 판매** | 작품의 의도·재료·제작 과정 설명, 관심 작품에 대한 질문 응대, 가격·판매 상태 안내와 구매 문의 연결 | 대화를 많이 했다는 사실만으로 실제 판매가 증가했다고 볼 수는 없음 |
| **다음 전시의 수익** | 관람 후 관심 있는 작가·작품의 소식과 다음 전시 안내 | 후속 안내와 실제 재방문·구매 결과를 구분해야 함 |

**현재 여러분이 구상한 도슨트와 더 직접적으로 이어지는 것은 작품 판매 쪽입니다.** 작가가 제공한 이야기를 듣고 작품을 이해한 관람객이, 해당 작품의 구매 가능 여부를 확인하고 문의할 수 있기 때문입니다. 이는 제품 설계상의 연결이며, 실제 구매 효과는 검증할 가설입니다.

예를 들어 다음과 같은 경험으로 만들 수 있습니다.

> 관람객이 작품의 표현 의도를 질문한다.  
> 도슨트가 작가가 승인한 자료로 설명한다.  
> 관람객이 구매에 관심을 보이면 등록된 가격과 판매 상태를 안내한다.  
> 해당 작품의 구매 문의나 주문을 생성하고, 운영자가 처리할 수 있게 한다.

이렇게 하면 도슨트가 **작품 설명과 구매 상담 사이의 반복 응대를 맡는 기능**으로 자리 잡습니다.

## 4. 대회에서는 ‘한 명이 무엇까지 할 수 있는가’를 보여주면 됩니다

이 방향으로 간다면 핵심 시연은 다음 정도면 충분히 명확합니다.

1. **운영자가 전시와 작품 정보를 등록합니다.**  
   작품 설명, 가격, 판매 여부 등을 확인하고 공개합니다.

2. **시스템이 전시 페이지와 관람객 응대 기능을 준비합니다.**  
   작품별 도슨트와 QR 등이 같은 자료를 바탕으로 만들어집니다.

> 회사 운영자는 필요한 예외만 처리한다.

여기에 이용료를 받는 구조가 있다면, **한 명이 여러 작가에게 유료 서비스를 제공하는 사업**이 됩니다. 전시 입장권이나 작품을 직접 판매하는 기능이 추가되어야만 One-Person Company가 성립하는 것은 아닙니다.

즉, **1번은 이미 대회 취지를 설명하는 데 필요한 사업 흐름을 갖출 수 있습니다.**

### ② 2번에는 새로운 고객 가설이 추가됩니다

지금까지 공유된 피드백은 작가가 관람객에게 작품을 충분히 설명하기 어렵다는 문제에 가깝습니다. 이는 1번의 출발점과 직접 이어집니다.

2번으로 넓히면 다음 가설도 확인해야 합니다.

- 작가나 기획자가 예매·판매·후속 관리에서 실제로 큰 부담을 느끼는가?
- 그 업무를 도슨트와 함께 처리하고 싶어 하는가?
- 이미 사용 중인 방식에서 새로운 통합 서비스로 옮길 이유가 있는가?
- 추가 기능이 이용료를 지불할 만큼 중요한가?

**1번도 유료 수요가 검증된 상태는 아닙니다.** 다만 2번은 기존 설명 수요에 더해, 전시 운영 도구를 함께 사용하려는 수요까지 확인해야 합니다.

그래서 현재 근거만으로는 1번이 적은 가정으로 이어집니다.

### ③ 2번에서는 도슨트의 역할을 한 번 더 입증해야 합니다

1번에서 도슨트는 고객이 구매하는 핵심 서비스입니다.

2번에서는 예매, 입장, 판매, 후속 관리가 제품의 큰 부분을 차지하므로, **도슨트가 그 과정에서 얼마나 중요한 역할을 하는지**를 설명해야 합니다.

특히 전시장 안에서만 사용하는 도슨트는 이미 구매한 입장권의 첫 구매를 유도했다고 설명하기 어렵습니다. 작품 판매와 연결하려면 작품 설명에서 구매 문의나 주문으로 실제로 넘어가는 경험을 만들어야 합니다.

그 연결이 구현되고 고객에게 필요하다면 2번은 강해집니다. 반대로 연결이 약하면 **여러 전시 운영 기능에 도슨트가 함께 들어 있는 제품**으로 보일 수 있습니다.

1번은 자료 입력부터 도슨트 제공까지의 흐름을 집중해서 완성할 수 있습니다.

2. **그 사람의 운영 문제가 확인됐다.**

3. **중요한 수익 흐름 하나를 끝까지 연결할 수 있다.**  
   예매·입장 또는 작품 문의·주문 중 하나를 선택하고, 운영 결과까지 반영할 수 있습니다.

4. **다음 전시도 같은 방식으로 운영할 수 있다.**  
   새로운 전시마다 팀이 맞춤 제작하지 않아도 됩니다.

이 조건이면 2번은 **고객의 실제 사업 운영을 제품이 맡는다는 점에서 더 강한 출품안**이 될 수 있습니다. 그 우위는 기능이 많아서 생기는 것이 아니라, 확인된 고객의 중요한 업무를 끝까지 처리해서 생깁니다.

아래의 2번은 대화에서 구체화한 **‘전시 단위의 운영·수익화 자동화’ 버전**을 기준으로 정리했습니다. 세부 기능, 과금 방식, MVP 범위는 현재까지 논의한 기획 제안이며, 실제 수요나 성과가 검증된 것으로 보지는 않습니다.

## 먼저 한눈에 비교

| 항목 | 1번: AI 도슨트 공급 회사 자동화 | 2번: 전시 사업 운영 자동화 |
|---|---|---|
| **사업의 중심** | 도슨트 서비스를 효율적으로 제작·제공하는 회사 | 전시의 고객 응대와 수익 업무를 연결하는 운영 서비스 |
| **1인 사업의 주체** | 우리 회사의 운영자 | 고객인 작가·독립 기획자 |
| **우리의 유료 고객** | 작가, 갤러리, 전시 운영자 | 전시를 직접 기획·운영하는 작가나 기획자 |
| **관람객의 역할** | AI 도슨트를 이용하는 최종 사용자 | 도슨트 이용자이자 잠재적인 입장권·작품 구매자 |
| **고객에게 주는 핵심 가치** | 작품 이야기를 쉽고 정확하게 도슨트로 만들어 관람객에게 전달 | 전시 개설부터 관람객 응대·거래 관리까지 혼자 처리하도록 지원 |
| **주요 자동화 대상** | 자료 수집·정리, 도슨트 생성·배포, 운영·고객 지원 | 전시 개설, 안내, 예매 또는 작품 문의·주문, 후속 관리 |
| **AI 도슨트의 위치** | 판매하는 핵심 서비스 | 전시 운영 과정에서 작품 설명과 관람객 응대를 담당하는 핵심 기능 |
| **우리 회사의 수익** | 도슨트 서비스 이용료 | 전시 운영 SaaS 이용료 등 |
| **입증해야 할 것** | 고객이 늘어도 제작·지원 업무를 한 명이 감당할 수 있는가? | 전시 운영자가 여러 업무를 혼자 처리할 수 있게 되는가? |

# 1. 두 안의 공통 출발점

## 1-1. 기존 AI 도슨트 아이디어

작가가 다음과 같은 정보를 제공하면, 관람객이 해당 정보를 바탕으로 AI 도슨트에게 질문할 수 있는 서비스입니다.

- 작가의 이력과 개인적인 경험
- 작품 세계와 전시의 주제
- 개별 작품의 설명
- 재료, 기법, 표현 방식
- 작품을 만들 때의 생각과 감정
- 관람객에게 전하고 싶은 이야기

관람객은 전시 페이지나 작품별 QR로 접속해 “왜 이런 색을 사용했나요?”, “이 표현에는 어떤 의미가 있나요?” 같은 질문을 합니다.

**두 안 모두 이 핵심을 유지합니다.** 차이는 도슨트를 중심으로 어떤 사업 과정을 자동화하느냐입니다.

## 1-2. 현재 확인한 문제와 아직 확인하지 못한 것

앞서 공유한 작가 피드백에서는 **관람객에게 작품을 일일이 설명하기 어렵고, 충분한 설명 없이 관람을 마치는 사람이 있다는 문제**가 드러났습니다.

이는 작품 설명·응대 수요에 대한 초기 신호입니다. 다만 다음 사항은 추가 검증이 필요합니다.

- 작가가 실제로 서비스를 사용할 의향이 있는가?
- 자료 입력과 확인에 어느 정도 시간을 들일 수 있는가?
- 관람객이 QR을 열고 질문하는가?
- 작가나 전시 운영자가 이용료를 지불하는가?
- 도슨트 외에 예매·판매·후속 관리까지 함께 처리하고 싶어 하는가?

특히 마지막 질문은 **2번을 선택할 때 추가로 확인해야 할 핵심 가설**입니다.

## 1-3. 두 안에 공통으로 적용할 운영 원칙

**작가가 승인한 자료를 작품 설명의 기준으로 삼습니다.** 작가의 생각과 감정이 자료에 없으면 AI가 임의로 만들어 사실처럼 설명하지 않습니다.

외부 미술 지식과 작가의 의도도 구분합니다. 표현 기법의 일반적인 배경은 외부 자료를 참고할 수 있지만, 특정 작가가 그 기법을 사용한 이유는 작가가 제공한 정보로 설명해야 합니다.

자동화는 자료 정리와 반복 응대를 담당하고, 작가는 설명의 정확성과 공개 범위를 확인합니다. 승인과 예외 처리가 남아 있는 구조도 충분히 자동화된 서비스로 설계할 수 있습니다.

# 2. 1번: AI 도슨트 공급 회사를 1인 운영하는 사업

## 2-1. 한 문장 정의

> **작가가 자신의 이야기와 작품 자료를 입력하면 도슨트 제작·게시·관람객 응대·운영 결과 정리까지 이어져, 한 명이 여러 작가의 전시에 서비스를 제공할 수 있는 AI 도슨트 SaaS.**

이 안의 중심은 **“우리가 도슨트 서비스를 판매하고 제공하는 회사를 어떻게 한 명이 운영할 것인가?”**입니다.

고객은 작품 설명을 전달할 수 있는 서비스를 구매하고, 우리 회사는 그 서비스를 제공하는 과정의 반복 작업을 자동화합니다.

## 2-2. 해결하려는 문제

### 작가·전시 운영자의 문제

작품을 설명할 내용은 있지만, 이를 관람객이 이용할 수 있는 형태로 정리하고 운영하는 데 수고가 듭니다. 작가가 현장에 계속 머물며 모든 질문에 답하기도 어렵습니다.

### 우리 회사의 운영 문제

고객마다 사람이 인터뷰하고, 전사문을 정리하고, 설명을 작성하고, 챗봇과 전시 페이지를 만들어 주면 고객 수가 늘 때 제작 업무도 함께 늘어납니다.

따라서 1번에서는 **신규 고객에게 도슨트가 제공되기까지의 수작업을 줄이는 것**이 중요한 과제입니다.

## 2-3. 전체 자동화 흐름

아래는 사업 전체의 구상입니다. 모든 항목을 해커톤에서 구현해야 한다는 뜻은 아닙니다.

| 단계 | 제안하는 자동화 내용 | 결과 |
|---|---|---|
| **① 고객 유입·신청** | 서비스 안내, 자주 묻는 질문 응대, 가입·신청 후 안내 | 작가가 서비스 이용을 시작 |
| **② 자료 입력** | 표준 질문지에 따라 작품 정보·이미지·설명을 입력하거나 녹음 | 도슨트 제작에 필요한 원자료 확보 |
| **③ 자료 정리** | 작가 이력, 작품 의도, 재료, 표현 방식 등을 작품별로 정리 | 도슨트용 자료와 설명 초안 생성 |
| **④ 작가 확인** | 내용 수정, 공개 범위 선택, 게시 승인 | 사용할 수 있는 승인 자료 확정 |
| **⑤ 도슨트 생성·배포** | 전시 페이지와 작품별 도슨트·QR 생성 | 관람객이 이용할 수 있는 서비스 제공 |
| **⑥ 관람객 응대** | 승인 자료를 근거로 질문에 답변 | 반복적인 작품 설명 제공 |
| **⑦ 운영 결과 정리** | 자주 나온 질문, 답하지 못한 질문, 관심 작품 등을 정리 | 작가가 보완할 내용과 관람 반응 확인 |
| **⑧ 고객 지원·재이용** | 수정 요청 접수, 이용 안내, 다음 전시 이용 안내 | 서비스 유지와 반복 이용 지원 |

여기서 가장 중요한 부분은 **② 자료 입력부터 ⑤ 배포까지가 고객별 맞춤 개발 없이 이어지는 것**입니다.

다음 작가가 들어올 때마다 팀원이 자료를 다시 편집하고 개발자가 챗봇을 새로 만들어야 한다면, 1인 운영의 설득력이 약해집니다.

## 2-4. 사람에게 남기는 역할

작가는 다음을 담당합니다.

- 자신의 이야기와 작품 자료 제공
- 설명의 정확성과 공개 범위 확인
- 자료에 없는 질문에 대한 추가 설명

우리 회사 운영자는 다음을 담당합니다.

- 서비스 품질과 시스템 상태 확인
- 자동으로 처리하기 어려운 고객 요청
- 오류와 특수한 상황 처리

목표는 **운영자가 고객마다 제작 전 과정을 직접 수행하는 부담을 줄이는 것**입니다.

## 2-5. AI 도슨트의 역할

1번에서는 AI 도슨트가 **고객이 구매하는 핵심 서비스**입니다.

고객이 얻는 가치는 작품 설명과 관람객 응대이고, 우리 회사의 자동화는 그 가치를 효율적으로 제공하기 위한 구조입니다. 기존 아이디어와 가장 직접적으로 연결됩니다.

## 2-6. 수익 모델 제안

검토할 수 있는 과금 방식은 다음과 같습니다.

- **전시별 이용료:** 전시 한 회 또는 일정 운영 기간에 대한 이용료
- **월 구독:** 반복적으로 전시를 운영하는 공간이나 고객을 위한 방식
- **규모별 요금:** 작품 수, 운영 기간, 이용량 등에 따른 구분

현재 가격이나 지불 의사가 검증된 것은 아닙니다. 초기에는 고객의 전시 운영 방식에 맞춰 과금 단위를 검토할 수 있습니다.

**입장료나 작품 판매 대금은 이 안에서 우리 회사의 기본 매출이 아닙니다. 우리 회사는 도슨트 서비스의 대가를 받습니다.**

## 2-7. 해커톤 MVP 제안

초기 시연은 **작가 한 명, 전시 한 개, 작품 세 점 정도**로 좁혀볼 수 있습니다.

핵심 기능은 다음과 같습니다.

1. 작품 자료 입력
2. 작품별 설명 초안 생성
3. 작가의 수정·승인
4. 전시 페이지·QR 게시
5. 관람객 질문과 미응답 질문 확인

화면은 **작가용 등록·승인 화면, 관람객용 도슨트 화면, 운영 결과 화면**으로 구성할 수 있습니다.

가능하다면 두 번째 전시를 같은 절차로 개설하는 장면도 보여주는 것이 좋습니다. 이는 새로운 고객이 들어와도 같은 제품을 반복해서 사용할 수 있다는 증거가 됩니다.

## 2-8. 검증할 핵심 지표

- 전시 하나를 개설할 때 **우리 회사 사람이 작업한 시간**
- 작가의 자료 입력·확인 시간
- 신규 고객마다 별도 개발이 필요한지
- 자동으로 처리된 문의와 사람이 처리한 문의
- 전시 한 건의 운영 비용
- 실제 사용 의향과 지불 의향

1번의 주요 검증 질문은 **“서비스를 원하는 고객이 있는가?”와 “그 서비스를 한 명이 반복해서 제공할 수 있는가?”**입니다.

# 3. 2번: 작가·기획자의 전시 사업을 1인 운영하도록 돕는 사업

## 3-1. 한 문장 정의

> **작가나 독립 기획자가 전시를 개설하고, 관람객에게 작품을 설명하며, 예매 또는 작품 거래와 후속 관리를 혼자 처리할 수 있도록 돕는 전시 운영 자동화 SaaS.**

이 안의 중심은 **“고객인 작가나 기획자가 전시 사업을 어떻게 한 명이 운영할 것인가?”**입니다.

도슨트는 전시 운영 과정에서 관람객과 대화하고 작품을 설명하는 역할을 맡습니다.

## 3-2. ‘전시 단위’와 One-Person Company의 관계

전시는 상품이나 프로젝트의 단위입니다. 사업 주체는 **그 전시를 기획·운영하며 수익을 얻는 작가 또는 독립 기획자**입니다.

따라서 전시마다 운영한다는 점이 1인 사업과 충돌하지는 않습니다. 같은 시스템으로 다음 전시나 다른 운영자의 전시도 개설할 수 있다면, 반복 가능한 사업 운영 도구라는 설명이 더 명확해집니다.

다만 이것은 대회 취지에 대한 해석이며, 공개 안내가 전시 사업의 포함 여부를 별도로 확정한 것은 아닙니다.

## 3-3. 초기 고객과 해결하려는 문제

초기 고객은 다음 중 하나로 좁히는 것이 좋겠습니다.

- 자신의 전시를 직접 준비하고 운영하는 작가
- 소규모 전시를 기획·운영하는 독립 기획자 또는 공간 운영자

고객이 겪는 문제의 가설은 다음과 같습니다.

- 전시 소개와 안내를 여러 곳에 반복해서 작성한다.
- 관람객의 일정·관람·작품 문의를 개별적으로 처리한다.
- 작품에 대한 관심이 생겨도 구매 문의로 이어지는 과정이 번거롭다.
- 판매 여부나 문의 처리 상태를 따로 관리한다.
- 전시가 끝나면 관심 관람객과의 관계가 끊긴다.

**이 문제들은 실제 고객에게 확인해야 합니다.** 기존 작가의 설명 수요 피드백만으로 모두 검증됐다고 볼 수는 없습니다.

## 3-4. 전체 자동화 흐름

1. **전시 개설**  
   전시 소개, 일정, 장소, 작품 자료, 선택한 판매 정보를 등록합니다.

2. **홍보·관람 안내**  
   등록한 자료로 전시 소개와 안내 콘텐츠를 만들고, 관람객이 필요한 정보를 확인하게 합니다.

3. **예매·입장 또는 작품 거래 연결**  
   해당 전시의 수익 모델에 맞춰 예매와 입장을 관리하거나, 작품 문의와 주문을 연결합니다.

4. **AI 도슨트 응대**  
   작가가 승인한 자료를 기반으로 작품을 설명하고 질문에 답합니다.

5. **문의·주문 상태 관리**  
   운영자가 처리해야 할 요청을 모으고, 처리 결과를 관람객 안내와 작품 상태에 반영합니다.

6. **관람 후 관계 유지**  
   구독에 동의한 관람객에게 작품 이야기나 다음 전시 소식을 안내합니다.

7. **운영 결과 확인**  
   관람객의 관심, 문의, 선택한 거래 흐름의 진행 상황 등을 정리합니다.

이 구조의 목표는 **전시 운영자가 여러 곳에 흩어진 반복 업무를 한 흐름으로 처리하게 하는 것**입니다.

## 3-5. 입장료와 작품 판매는 구분해서 설계

모든 전시가 입장료와 작품 판매를 함께 수익 모델로 갖는다고 가정할 필요는 없습니다.

| 구분 | 입장료 중심 전시 | 작품 판매 중심 전시 |
|---|---|---|
| **주요 거래** | 입장권 예매·구매 | 작품 구매 문의·주문·결제 |
| **거래가 발생하는 시점** | 주로 관람 전 | 관람 전·중·후 가능 |
| **도슨트가 기여할 수 있는 역할** | 방문 전 전시 소개와 사전 질문 응대 | 작품 이해, 관심 구체화, 구매 가능 여부 안내와 문의 연결 |
| **운영 자동화의 예** | 관람 안내, 예약 확인, 입장 상태 관리 | 문의 접수, 구매 상담 연결, 주문·판매 상태 관리 |
| **초기 시연에서 보여줄 결과** | 예매 또는 입장 처리의 완료 | 문의 처리 또는 구현한 거래 단계의 완료 |

전시장 안에서만 사용하는 도슨트가 이미 구입한 입장권의 첫 구매를 만들었다고 설명하기는 어렵습니다. 입장료 수익과 연결하려면 **관람 전 접점에서 어떤 도움을 주는지**를 설계해야 합니다.

작품 판매는 현재 도슨트 구상과 상대적으로 직접 연결하기 쉽습니다. 작품에 대해 대화하던 관람객이 구매 가능 여부를 확인하고 문의하는 흐름을 만들 수 있기 때문입니다. 다만 판매 효과는 검증할 가설입니다.

## 3-6. AI 도슨트의 역할

2번에서 도슨트는 **작품 설명과 구매 관련 응대 사이를 연결하는 접점**이 될 수 있습니다.

예를 들어 다음과 같은 경험입니다.

- 관람객이 작품의 표현 의도를 질문합니다.
- 도슨트가 작가가 승인한 자료로 설명합니다.
- 관람객이 구매에 관심을 보이면 등록된 가격과 판매 상태를 안내합니다.
- 해당 작품의 구매 문의 또는 주문을 생성합니다.
- 운영자가 처리한 결과가 작품 상태와 후속 안내에 반영됩니다.

가격이나 판매 여부는 운영자가 등록한 정보에 근거해야 합니다. 작품이 판매된 뒤에는 관련 안내도 갱신되어야 합니다.

**도슨트가 있다는 사실만으로 매출 증가가 입증되는 것은 아닙니다.** 대화가 문의나 주문으로 이어지는지, 실제로 운영자의 업무를 줄이는지 확인해야 합니다.

## 3-7. 사람에게 남기는 역할

작가·전시 운영자는 다음을 판단합니다.

- 작품 설명과 공개 범위
- 가격과 거래 조건
- 특수한 구매 문의와 예외 상황
- 현장 설치·운송 등 실제 작업

시스템은 승인된 정보를 바탕으로 안내, 접수, 상태 반영, 후속 연락 같은 반복 처리를 담당합니다.

따라서 제품이 맡는 범위를 **전시의 고객 응대와 디지털 운영·거래 관리**로 명확히 설명하는 것이 좋겠습니다.

## 3-8. 수익 모델 제안

### 고객인 전시 운영자의 수익

전시의 성격에 따라 입장료 또는 작품 판매 대금 등이 발생합니다.

### 우리 회사의 수익

우리 회사는 전시 운영 서비스를 제공한 대가를 받습니다.

- 전시별 이용료
- 반복 운영자를 위한 구독료
- 실제 거래를 연결하는 구조라면 검토할 수 있는 거래 수수료

**전시 운영자의 작품 판매액 전체를 우리 회사 매출로 표현하면 안 됩니다.** 고객의 사업 매출과 우리 SaaS의 매출을 구분해야 합니다.

## 3-9. 해커톤 MVP 제안

2번은 **하나의 수익 흐름을 선택해서 완성하는 것**을 추천합니다.

현재 도슨트의 강점을 살리는 예시는 **작품 구매 문의를 연결하는 전시**입니다.

핵심 기능은 다음과 같습니다.

1. 전시·작품 설명과 가격·판매 상태 등록
2. 작가의 확인과 전시 페이지·QR 게시
3. 도슨트 대화
4. 특정 작품의 구매 문의 생성
5. 운영자의 문의 처리와 상태 반영

여기까지 구현했다면 **‘작품 설명과 구매 문의 관리 자동화’**라고 설명할 수 있습니다.

주문과 결제까지 연결했다면 그 범위까지 말할 수 있지만, 문의 접수만으로 판매가 완료됐다고 표현해서는 안 됩니다. 실제 결제 연동은 별도로 범위를 확인해야 하며, 시뮬레이션을 사용한 경우에도 구분해 보여주는 것이 좋습니다.

## 3-10. 검증할 핵심 지표

- 전시 개설과 운영에 필요한 고객의 작업 시간
- 관람객 문의 중 자동으로 처리된 비율
- 문의를 접수하고 처리하는 데 걸린 시간
- 도슨트 대화가 구매 문의로 이어지는 비율
- 문의가 실제 주문·구매로 이어지는 결과
- 다음 전시에도 사용할 의향과 지불 의향

2번의 주요 검증 질문은 **“전시 운영자가 이 업무들을 함께 처리하기를 원하는가?”와 “제품이 실제 사업 운영을 더 쉽게 만드는가?”**입니다.

# 5. MAWD 트랙 2와의 연결

공식 모집글은 **1인이 운영 가능한 AI 자동화 프로그램**과 **파트너 API 또는 데이터를 핵심으로 활용하는 자동화 SaaS**를 제시합니다. MVP 완성도와 시장 반응 등도 평가한다고 안내합니다. 다만 공급 회사와 고객 중 누구의 1인 운영을 우선하는지, 두 방식 중 어느 쪽에 더 높은 점수를 주는지는 공개하지 않았습니다. :chatgpt-content-reference{index="4"}

따라서 두 안은 다음 논리로 연결됩니다.

### 1번의 연결

**“우리 회사가 도슨트 서비스를 여러 고객에게 한 명으로 제공할 수 있다.”**

신규 작가가 자료를 입력한 뒤 서비스가 생성·제공되는 흐름이 핵심 증거입니다. 고객이 늘어도 공급자의 제작 업무가 그대로 늘지 않도록 설계해야 합니다.

### 2번의 연결

**“고객인 작가·기획자가 전시 사업을 한 명으로 운영할 수 있다.”**

전시를 개설하고 관람객을 응대하며 선택한 거래 흐름을 관리하는 과정이 핵심 증거입니다. 다음 전시도 같은 절차로 운영할 수 있게 하면 제품의 반복 사용 가능성이 명확해집니다.

**두 안 모두 적용 가능한 해석입니다.** 2번이 전시 단위라는 이유로 제외되는 것은 아니며, 1번이 다루는 기능이 상대적으로 좁다는 이유로 사업성이 부족한 것도 아닙니다.

# 6. 두 안의 장단점과 현재 판단

| 비교 기준 | 1번 | 2번 |
|---|---|---|
| **주제 설명의 직접성** | 우리 회사 자체의 1인 운영이어서 설명이 간결함 | 고객의 전시 운영이 사업이라는 주체를 명확히 해야 함 |
| **기존 아이디어와의 연결** | 도슨트가 핵심 상품으로 유지됨 | 도슨트가 전시 운영 과정의 기능으로 확장됨 |
| **현재 작가 피드백과의 연결** | 작품 설명·응대 문제에 직접 연결 | 운영·판매 관리 수요를 추가로 확인해야 함 |
| **고객에게 보여주는 가치** | 도슨트를 쉽게 만들어 운영 | 여러 전시 업무를 함께 처리 |
| **시연의 강점** | 신청한 고객에게 서비스가 자동으로 제공되는 과정 | 관람객의 관심이 문의·거래 행동으로 이어지는 과정 |
| **구현 범위** | 상대적으로 좁은 흐름을 완결하기 쉬움 | 수익 모델을 좁히지 않으면 범위가 커짐 |
| **주요 실패 형태** | 핵심 제작은 수작업인데 주변 업무만 자동화 | 기능은 많지만 문의·거래·운영 상태가 연결되지 않음 |
| **추가 검증의 중심** | 도슨트 이용료를 낼 이유와 공급 업무 절감 | 통합 운영 수요와 고객의 실제 업무 절감 |
| **현재 추천** | **우선 추천** | **구체적인 운영 수요를 확보하면 유력한 대안** |

## 현재 1번을 우선 추천하는 이유

지금까지 확인한 문제는 작품 설명과 관람객 응대에 가깝습니다. 1번은 이 문제에서 바로 출발할 수 있고, 도슨트 제공 과정을 비교적 좁은 범위로 완결해 보여줄 수 있습니다.

또한 1번도 이용료를 받는 사업입니다. **입장료나 작품 판매를 추가해야만 수익을 내는 1인 회사가 되는 것은 아닙니다.**

## 2번을 선택할 이유가 강해지는 조건

다음 조건이 확보되면 2번의 장점이 커집니다.

- 전시를 실제 사업으로 운영하는 고객이 있다.
- 그 고객이 문의·예매·판매·후속 관리에서 반복적인 어려움을 겪는다.
- 그중 중요한 흐름 하나를 해커톤에서 완결할 수 있다.
- 다음 전시나 다른 운영자도 같은 방식으로 사용할 수 있다.

그때는 **실제 고객의 사업 운영을 제품이 맡는다는 점**에서 2번이 더 강한 출품안이 될 수 있습니다.

# 7. 팀에서 결정할 때 사용할 기준

**1번을 선택한다면**, 기획의 중심 질문은 다음입니다.

> “작가의 이야기를 관람객이 질문할 수 있는 도슨트로 만들고, 이 서비스를 한 명이 여러 전시에 반복해서 제공하려면 어떤 작업을 자동화해야 하는가?”

**2번을 선택한다면**, 기획의 중심 질문은 다음입니다.

> “작가나 기획자가 전시를 사업으로 운영할 때 가장 부담스러운 고객 응대·거래 업무는 무엇이며, 도슨트를 포함한 하나의 흐름으로 이를 어떻게 처리할 것인가?”

현재 확보한 문제에 집중하려면 **1번**, 실제 전시 운영자의 더 넓은 업무 문제를 확인했다면 **2번**이 적절합니다. 어느 쪽이든 해커톤에서는 **고객이 입력한 정보가 서비스 제공과 운영 결과까지 이어지는 하나의 완결된 흐름**을 보여주는 것을 우선하는 것이 좋겠습니다.
