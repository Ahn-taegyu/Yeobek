# 기준과 기존 결함

[요청 원문](../references/user-harness-playbooks-plan.md)은 `e3c05f0`을 기준으로 한다. 실제 후속 작업의 기반 `e20bd2f`는 그 자손이며 아래 네 결함을 이미 수정했다. [기존 수정 검토](ai-harness-fix-review.md)의 재현 및 검증 기록을 인용하며 이번 문서 작성에서 재실행했다는 뜻은 아니다.

| `e3c05f0`에서 보고된 문제 | `e20bd2f`의 기존 수정 기록 |
| --- | --- |
| 601자 승인 해설이 일반 질문을 막음 | 승인본 2,000자와 생성 답 600자 분리 |
| `18`, `18번`이 해설 요청으로 처리되지 않음 | 단독 번호를 해설로 처리 |
| 일반 해설 요청이 승인 해설 대신 생성됨 | 안전하게 식별된 표현은 승인 해설 재사용 |
| `천 번을`, `이 번에`가 번호로 오인됨 | 명확한 횟수·지시어를 제외하고 모호한 경우 확인 |

기존 수정을 되돌리지 않고 제안된 해설 초안 전용 계약, 없는 번호 안내 등 남은 요구를 기존 동작과 대조해 적용한다. 기존 검토는 실제 호출 0회와 모의 평가의 한계를 기록한다.

# 0단계에 기록한 구조 평가와 대응

| 기존 로컬 문서에서 확인한 요소 | 제안된 대응 | 상태와 한계 |
| --- | --- | --- |
| [제품 플러그인](../specs/product-ai-plugin.md)의 업무별 스킬·도구 매핑과 정적 지문 | manifest에 순서 있는 단계와 지문 포함, 실행 기록과 누락 검사 | 2단계 제안; 현 구조가 순서 실행을 증명한다는 뜻은 아님 |
| 같은 문서의 pstack 업무 절차·스킬 조합 참고 | 업무별 서버 실행 절차에 단계 적용 | 외부 도구의 현재 기능을 새로 검증하거나 권한을 이식한 것은 아님 |
| [기존 검토](ai-harness-fix-review.md)의 `assertPluginTool` 구성 일관성 검사 한계 | 선언된 저장소 함수만 제공하는 capability 객체 | 2단계 제안; 기존 검사는 인가 경계가 아님 |
| 모의 평가·실호출 0회 | 해설 초안 실호출·비교·사람 라벨 | 3단계 계획만; 키·migration과 별도 승인 필요 |
| 해설 초안과 관람 답의 공통 검증, 모듈별 실패 표현과 시간 제한 | 해설 전용 스키마·오류 대응표·공통 deadline | 1단계 제안; 동작과 기존 회귀를 보존하며 검증 |

3단계는 별도 승인 전 실행하지 않는다. 4단계는 게시 기능 이후로 남긴다. 상세 계획과 검증은 [하네스](../specs/ai-harness.md), [플러그인](../specs/product-ai-plugin.md) 및 원문을 따른다.

# 단계별 실행 기록

0단계는 요청 원문·추가 검토 메모를 각각 SRC-029·030으로 보존하고 기존 기획과 연결했다. 문서 검사 104개·검색 회귀 9개가 통과했으며, 최초 기준 앱 검사 225개·lint·typecheck·build·모의 비교도 통과했다. PR #2의 최신 수정 `e20bd2f`에서 새 브랜치를 분기했다.

1단계는 해설 전용 최대 2,000자 스키마와 600자 초과 `overTarget` 경고, 명시 의도 우선의 단일 판별 함수, 미존재·비공개 번호의 동일 고정 안내를 구현했다. 관람 생성 답 600자와 승인본 원문 검증은 유지한다. `제 3번 질문은`은 선택된 작품에 대한 질문으로 처리하며 다른 작품을 조회하지 않는 회귀 검사가 통과했다. 기본값이 생략된 입력의 의미를 지우지 않도록 원래 의도 존재 여부를 보존하고, 예전 내부 `auto` 값은 제거했다.

오류 클래스·보류 결과는 그대로 두고 순수 대응 함수로 향후 HTTP 상태·코드·재시도 여부를 정리했다. 공통 deadline으로 통합하되 Sol 교차 검토에서 발견한 취소 전파 중단, 취소/시간 초과 경합의 우선순위, 같은 턴 취소 시 저장소 호출 지연을 보완했다. 부모 에이전트가 실제 diff를 검토하고 전체 **284개** 단위 검사·번들 일치·lint·typecheck·build·모의 5사례 비교를 직접 통과시켰다. 실제 제공사 호출은 0회이며 HTTP·DB 변경은 없다.

2단계는 플러그인 0.4.0의 다섯 업무에 순서 있는 단계를 선언하고, 실행기에 순서·중복·동시 실행·누락 검사를 넣었다. 정상 조기 반환은 생략 이유를 명시하고 운영 오류는 실패 기록과 원래 오류를 보존한다. 선언하지 않은 저장소 함수는 capability 객체의 타입과 런타임 키에 없다. 이 제한은 업무별 함수 노출 범위이며 개별 단계 콜백의 의미나 DB 인증을 검증하지 않는다. 스킬의 서버 검색 설명도 명세로 옮겼다.

Sol 구현을 별도 Sol이 교차 검토하고 부모가 실제 diff와 기존 동작을 대조했다. 저장 직전 취소, 후보 조립 중 오류가 실행 기록 오류에 가려지는 문제, 동적 업무 선택의 타입 과장, 후보 라운드 직후 취소 우선순위를 수정하고 회귀를 추가했다. 공개 문맥이 확인된 관람 승인본·고정 응답의 최종 공개 재검사, 후보 병렬 생성·기존 호출 예산, 자료 적용 재요청·동시 적용 복구도 보존했다. 내부 기록은 관람 답변·해설 부모/평가 라운드·자료 정리/적용 결과에 남기며 실제 게시·저장·HTTP 응답으로 연결한 것은 아니다.

부모가 최종 코드에서 단위 **300개**, lint·typecheck·프로덕션 build·번들 일치·모의 5사례 비교를 직접 통과시켰다. 문서 104개·기능 23개·Bases 3개에 검사 오류가 없고 검색 회귀 9개가 통과했다. DB·HTTP·의존성은 변경하지 않았으며 기존 로컬 DB를 초기화하거나 새 통합 검사를 실행하지 않았다. 3~4단계는 계획으로 남아 있으며 실 제공사 호출은 0회다. 모의 비교 수치는 실제 품질·비용·응답 시간의 근거로 사용하지 않는다.

# 원자료의 상세 재현 기록

[Claude 검토 메모](../references/claude-ai-harness-review-notes.md)에 기록된 **과거 `e3c05f0` 재현**이다. 작성자는 합성 publication/request fixture와 항상 `answered`를 반환하는 가짜 제공사로 임시 단위 테스트를 실행하고 삭제했다고 밝혔다. fixture 번호 18 외 조회는 null을 돌렸으며 실 제공사 호출은 없었다. 아래는 전달된 관찰이지 현 커밋에서 재실행한 결과가 아니다.

| 입력과 관찰 | 메모가 기록한 원인과 기획 기준 |
| --- | --- |
| 600자 승인 해설과 일반 질문은 `answered`, 모델 1회; 601자는 `invalid_context`, 0회 | 전체 문맥 검증이 해설을 관람 답변 상한 600자로 검사. 기능명세 4.1은 목표 600자, 저장·승인 최대 2,000자 및 초과 경고; DB도 2,000자 |
| 미선택 `18`은 `clarify`, 0회; 다른 작품 선택 후 `18`은 이전 작품 질문으로 생성 1회; 선택 후 `18번`은 18번 조회 후 생성 1회 | 당시 번호 판별은 `번`을, 해설 판별은 설명 표현을 요구. BR-09는 숫자만 전송하면 해당 번호 해설 요청 |
| `이 작품 설명해줘`는 승인본, 0회; `이 작품에 대해 알려줘`, `작품 소개해 주세요`, `설명 부탁해요`, `해설 들려줘`는 각각 생성 1회 | 당시 해설 정규식이 제한적이고 의도 필드가 없음. BR-10은 기본 해설에 승인본 그대로 사용 |
| `천 번을 봐도 좋네요. 재료가 뭔가요?`는 1000, `이 번에 본 작품 재료는 뭔가요?`는 2로 해석하여 둘 다 `publication_unavailable`, 0회 | 한글 수사 뒤 조사도 번호로 인정. BR-09는 연도·수량을 자동으로 작품 번호로 바꾸지 않으며 EX-24는 없는 번호에 같은 안내와 현재 작품 유지를 요구 |

같은 메모의 `2024년에 만들었어?`와 `한 번 더 설명해줘`는 번호 없음, `3번과 5번`과 `3번이랑 5번`은 `[3, 5]`로 확인 요청, `제 3번 질문은`은 `[3]`으로 작품 번호 오판 가능성이 기록되었다. 마지막 사례는 위 1단계에서 별도 회귀로 확인·수정했다. 메모는 생성 답의 URL이 `invalid_output`으로 거부될 수 있다는 점도 기록한다.

# pstack 대응표의 출처와 범위

아래는 [원자료](../references/claude-ai-harness-review-notes.md)의 비교와 평가를 요약한 것이다. 작성자는 pstack `poteto-mode` 라우터 페이지를 요약 도구로 읽었고 개별 하위 스킬과 플레이북 단계 파일은 읽지 않았다고 명시했다. 따라서 아래 pstack 설명은 그 제한된 메모에 귀속되며 외부 전체 구현에 대한 독립 검증이 아니다. Yeobek 열도 `e3c05f0` 당시 상태다.

| 메모가 비교한 요소 | 당시 Yeobek 대응과 평가 | 후속 계획 |
| --- | --- | --- |
| 작업별 플레이북 선택 | 서버가 업무 선택; 제품 환경에 맞는 변형 | 서버 선택 유지 |
| 독립 스킬 파일 | 이름·설명 있는 다섯 스킬 | 버전 관리 유지 |
| 공통 원칙 | `instructions.md` 공통 지침 | 공통 지침 유지 |
| 순서 있는 단계와 생략 이유 | manifest에는 목록만 있고 순서는 코드 안에 있음 | 2단계 선언·실행 기록·누락 검사 제안 |
| 실제 호출 도구 | 모델 도구 없음; `assertPluginTool`은 상수 일관성 확인 | 2단계 capability 제안 |
| 실물을 통한 검증 | 모의 제공사만 사용, 실호출 0회 | 3단계 실호출·사람 평가 계획 |
| 두 번째 모델의 독립 판정 | 해설에 Liner 생성·OpenAI 평가·최대 1회 재생성; 관람 답변에는 없음 | 범위와 실측 한계 유지 |
| 측정·추론·추측 구분 | 문서 상태 및 답변 결과를 구분 | 주장과 검증 근거 분리 유지 |
| 스킬 변경·평가 플레이북 | 번들 지문과 비교 틀만으로 문장 변경의 품질 영향 확인 불가 | 3단계 스킬 변경 시 실호출 평가·지문 기록 제안 |

핵심 차이 두 가지는 **선언된 단계의 누락이 드러나지 않는 것**과 **실제 모델·사람 평가에 닿지 않는 것**이다. 고정 문구·승인본 재사용·출력 및 인용 검사는 모델과 무관하지만 관람 답변의 말투·근거 충실도는 프롬프트에 의존한다는 것이 원자료의 평가다. `retrieve-wiki`의 서버 검색 설명과 모델 지침도 구분한다. 3단계는 키·migration과 별도 승인 이후, 4단계는 게시 기능 이후의 계획이다.
